# Soundness: what a Janus theorem means

A verified Janus theorem is a Lean theorem about `Extracted.program`: the instruction words
copied out of the ELF binary, run by the Lean AArch64 model. The Lean kernel checks the proof;
nobody checks that the *statement* says what you meant. The guarantee is exactly the printed
statement, including its preconditions and quantifiers.

**The printed statement is the checked one.** `janus verify` prints the statement in a clean
environment (only `Janus` and `Extracted`, never the proof, so no proof-side notation,
unexpander or instance applies), and then checks that the text means what the kernel proved:
every argument in an instance-implicit position must be a registered instance of that trusted
environment or an instance binder of the theorem (no inline `⟨fun a b => a + b⟩` passed as the
`HMul` instance, which the default printer would show as `x * y`), and the printed text is
re-parsed and re-elaborated there and must be definitionally equal to the checked type (checked
by the elaborator at default transparency and confirmed by the kernel; definitionally equal
propositions are the same proposition, so the printed text, read with the canonical instances,
is exactly what was proved). `verified.json` also has `statementExplicit`, the statement with
every implicit and instance argument shown. The body of each plain proof-local `def` the
statement names (disclosed in `definitions`, and part of what the guarantee means) is held to the
same instance check, so a `def` whose displayed body reads as one operation while an inline
instance makes it compute another is rejected. See CRITICAL-1 in
[AUDIT-ROUND2.md](AUDIT-ROUND2.md) and R1 in [AUDIT-ROUND3.md](AUDIT-ROUND3.md).

## Trusted computing base

These are trusted, not proved.

1. **The Lean AArch64 model** (`Janus/Arm64/Decode.lean`, `Exec.lean`, `Vector.lean`,
   `State.lean`, for Advanced SIMD beyond the original subset `NeonInstr.lean`,
   `DecodeNeon.lean`, `Neon.lean`, `NeonFP.lean`, `ExecNeon.lean`, and the crypto/CRC32/permute
   files `InstrCrypto.lean`, `DecodeCrypto.lean`, `ExecCrypto.lean`, `Crypto.lean`): the decoder, the instruction semantics and the checked memory. They are meant to agree with the
   Arm Architecture Reference Manual (ARM ARM) for the supported user-mode A64 subset. That
   agreement is differentially tested against qemu (`janus-oracle`), not proved. If the model
   is wrong about an instruction the program uses, a theorem can be true of the model and false
   of the hardware. Words outside the supported subset fault (`undecodable`). They are never
   given a guessed meaning. The same holds for **the Lean x86-64 model**
   (`Janus/Amd64/Decode.lean`, `Instr.lean`, `Exec.lean`, `State.lean`, `Float.lean`, and the
   x87 FPU of C `long double`, `X87.lean` and `X87Exec.lean`; [AMD64.md](AMD64.md)), checked
   against the host CPU by the native oracle (`docs/ORACLE-AMD64.md`).
2. **The ELF word copy** (`cmd/janus`: `binary.go`, `extract.go`, `identity.go`): finding the
   symbol's `[addr, addr+size)` in `.text` and copying its little-endian 32-bit words (trailing
   zero padding words are dropped). `janus verify` re-runs this copy against the binary
   (checked by SHA-256) and compares it byte for byte with `Extracted.lean`, so a stale or
   edited extraction is rejected. The copy itself and the symbol table lookup are trusted.
3. **Stub classification**: the extractor treats as `panic` stubs the go1.26 runtime's panic
   functions and as `morestack` stubs `runtime.morestack.abi0`/`runtime.morestack_noctxt.abi0`,
   by exact ELF symbol name, only in a binary with a symbol table and only when the name is
   unique (docs/AUDIT-ROUND6.md F3, docs/AUDIT-ROUND7.md G1: any package can define an
   assembly function or push a `//go:linkname` named `runtime.panicX`; the runtime's own
   definition makes a same-ABI copy a link error and an other-ABI copy a mangled name). That
   argument needs the runtime to define every listed name, which round 7 read from the
   build-info Go version, a label `-ldflags=-X runtime.buildVersion=…` sets: a binary linked by
   go1.25 (whose runtime has no `panicSimdImm`) and labelled go1.26.0 carried an ordinary
   function under that name (round 8 G3). So the build-info version plays no part any more.
   A listed name is a stub only if **its code is pinned** (`cmd/janus/stubpin.go`, table
   `cmd/janus/stubpins_gen.go`, generated by `scripts/gen-stubpins.sh` from pinned toolchains,
   today go1.26.0, go1.26.5, go1.26.8 and go1.26.10):
   * The pclntab has a function starting at that address with that name (without `.abi0`), in
     package `runtime`, and the file at its entry is the pinned file of the toolchain's
     source tree (`runtime/panic.go`, `runtime/asm_arm64.s`, …; with `-trimpath` the path is
     exactly that, without it the part after the last `/src/`).
   * The SHA-256 of its normalized code is one of the pinned hashes for that GOARCH and name.
     Normalization masks every PC-relative field (arm64: B/BL, B.cond, CBZ/CBNZ, TBZ/TBNZ,
     ADR, LDR-literal, and ADRP with the ADD/LDR/STR that completes the address; amd64:
     rel8/rel32 and RIP-relative displacements, located by x86asm's `PCRelOff`) to zero and
     records the target as a symbol identity: `function+offset` or `datasymbol+offset` from
     the ELF symbol table; for type descriptors, which have no symbol, `type:<name>#<type
     hash>` read from the descriptor; for the two symbol-less read-only areas, string literals
     and anonymous static data (an error value's string header), only the area
     (`@go:string.*`, `@static`). All other bytes (opcodes, registers, immediates, frame
     sizes) are compared exactly. This is the weakest normalization that is stable. Measured
     on go1.26.0, both architectures, over the example binary, the round-7 fixture (arm64)
     and `scripts/stubpins` (which links every listed stub): of the names present in two or
     more programs, raw SHA-256 is stable for 5 of 34; masking only branch/call fields for
     17 of 34 (the ADRP+ADD/LEA data addresses move); the normalized form for 34 of 34. For
     every toolchain above, the normalized form is identical across programs within each build
     mode (the generator fails otherwise), and `-trimpath` and `-ldflags=-w` change nothing.
     Some modes compile the runtime differently, and each gets its own pin: `-gcflags=all=-N
     -l` (gopanic, panicdottypeI, panicwrap and six helpers), GOARM64 v8.1/v9.0 (gopanic only); GOAMD64 v2–v4
     change nothing. PIE is measured but not pinned (extraction rejects ET_DYN; on amd64 the
     linker rewrites TLS accesses, so throw, morestack.abi0, panicwrap and
     funcNamePiecesForPrint differ; arm64 PIE is identical). Stripped binaries have no symbol table and are rejected first. Across
     go1.26.x, only `runtime.concatstrings` changed (go1.26.5).
   * A stub's callees are pinned with it. For every stub except the terminal ones (gopanic,
     morestack, whose code *is* the outcome and whose callees are most of the runtime), every
     function it calls or jumps to must be a stub that passes the same check or one of the
     pinned helpers (`stubPinHelpers`: panicCheck1/2, convT*, throw, concatstring*, …),
     whose code is pinned the same way; a helper's own callees are not followed.
   A listed name that fails any check is an extraction error (and `janus verify`, which
   re-extracts, rejects an older extraction), never a stub and never code. Residual: the pin
   is on code bytes, not provenance. A binary that reproduces a pinned function byte for byte
   (assembly `WORD`s) with a forged pclntab file (`#line`) passes; its code is then the
   runtime's code, so it behaves as the runtime's except through what the pin does not fix:
   the bytes of string literals and anonymous static data (messages and error values, which
   no pinned code branches on), and the callees of helpers and of gopanic/morestack, which
   are identified by name only (each must then be a name the linking runtime lacks, defined
   by another package). Reaching a stub address ends the run with that outcome. This only
   affects theorems that mention stub outcomes (`Panics`, `NeverPanics`, `GrowsStack`). `Returns`
   cannot be established through a stub. Panics that Go raises from a hardware trap (a nil
   dereference is a `SIGSEGV`, turned into a panic by `runtime.sigpanic`) are not stub calls:
   the model reports them as faults, and `NeverPanics` excludes faults too.
   The same pin authenticates the runtime functions a framework contract library describes
   (`runtimeContractStubs`: the interface runtime's `convT*`, `assertE2I(2)`, `typeAssert`,
   `interfaceSwitch`, `efaceeq`, `ifaceeq`): a `--contract` that names one is accepted only if
   the function passes the checks above (its callees are identified by name only), and the
   extraction records it as `"pinned": true`, so the contract hypothesis of a theorem is about the
   runtime's own code. Other `--contract` names are not pinned (a contract over arbitrary code
   is still sound: the theorem holds for whatever code satisfies it).
   The extractor also classifies `runtime.cgocall`, `_cgo_topofstack` and `runtime.cgoUse` as
   `external` stubs (the cgo boundary): a run ends there too, and only the contract semantics of
   `Janus.FFI` (`ReturnsC`, with the contract named in the statement) continues past them; see
   "FFI (cgo)" below.
4. **The Lean kernel**, plus the verifier's hashing, process execution, axiom audit and
   statement audit (`Janus/Tools/Audit.lean`, including Lean's parser, elaborator and
   pretty-printer as used by the round-trip check above). The auditor and `leanchecker` load
   `.olean` files written by the sandboxed (untrusted) compile; Lean's `.olean` loader does not
   validate the structure of the compacted region it maps, so its robustness against a
   malformed `.olean` is part of the trusted base too. The
   audit allows only `propext`, `Quot.sound` and `Classical.choice`. It rejects `sorryAx`,
   `Lean.ofReduceBool` and `Lean.trustCompiler`, so `native_decide` and `bv_decide` cannot be
   used. `leanchecker` independently replays the environment (below).
5. **The Lean toolchain's own library** (`Init`, `Std`, `Lean`, `Lake`, shipped with the
   toolchain and read-only to every sandboxed process) and the **trusted framework build**: the
   framework's `.olean` files compiled by `janus` itself from the framework sources it carries,
   outside the sandbox, once per framework version (`janus verify --fresh` rebuilds them).

**What the kernel replay covers.** After the audit, `leanchecker` (shipped with the toolchain)
replays, through the kernel, **every module of the theorem's import closure that is not Lean
core**: every `Janus.*` framework module the theorem's environment imports, `Extracted`, the
independent `JanusTrusted` copy, every consumer module and every dependency module. Each module
is replayed against its imports as loaded from their `.olean` files, and since every non-core
import is itself replayed, no non-core declaration is taken on trust. Lean core is not replayed
by default; `--replay-fresh` additionally runs `leanchecker --fresh` on the theorem's module,
which re-adds every constant of its environment, core included, to an empty environment
(minutes: about 140 s for a closure that imports `Lean`). Passing replays are cached in the
trusted cache (`v1/replay`, never writable by a sandboxed process) under a key covering the
toolchain (its version, the `lean` and `leanchecker` binaries and its library), the module's
`.olean` bytes (with its `.server`/`.private` parts) and, recursively, the keys of its imports,
so an unchanged framework module is not replayed again while any byte change to it or to
anything below it is. Every marker carries an HMAC-SHA256 of its kind and key under the cache's
hidden key (the result cache's key, below), so a marker janus did not write (planted, copied from
another cache, or written before markers were authenticated) is a miss and the replay runs. The
cache is off with `--fresh` and without a sandbox (except that the framework replay verdict
below is read, never written, without a sandbox). Before replaying, every module of the closure
must resolve from its home: core modules from the toolchain library, `Janus.*` modules from the
trusted framework build and only modules the framework has a source for, `Extracted`/`JanusTrusted`
from the trusted directory.

**The framework replay verdict** (`cmd/janus/replaymark.go`). The kernel replay of the framework
(`leanchecker Janus`, every `Janus.*` module of the trusted build, each against its imports as
loaded from their `.olean` files) has one outcome per framework build: it depends only on the
toolchain and on the bytes of the framework's module-data files. So janus records it once, as a
verdict in `v1/replay/framework/<key>`, and reuses it:

* **Key.** SHA-256 over the toolchain's identity (`cacheID`: version, the `lean` and
  `leanchecker` binaries, the toolchain library) and the framework pins: the SHA-256 of every
  module-data file (`.olean`, `.olean.server`, `.olean.private`, `.ir`) of every framework module,
  taken right after the trusted build and re-checked after every later step. Editing any
  framework file changes the rebuilt module's bytes, hence the pins and the key; adding, removing
  or renaming a module changes the pin set; another toolchain changes `cacheID`. A verdict can
  therefore never be reused for other bytes (no stale verdict after a framework edit), and a
  verdict for an identical rebuild (same bytes) is correctly the same verdict.
* **Authenticity.** The verdict file holds an HMAC-SHA256 of `framework` and the key under the
  cache's hidden key (`v1/result/.key`, mode 0600 in a 0700 directory, the round-8 checks of
  `checkCacheRoot`/`readPrivateFile` apply; sandboxed processes see an empty tmpfs there). It is
  read with `O_NOFOLLOW` and must be a regular file of this user. A planted file, a verdict copied
  from another cache (another key), a verdict renamed to another framework's key, a module marker
  or other marker kind presented as a verdict, and a truncated or altered MAC are all misses
  (`TestFrameworkVerdictAuthentic`). Only janus writes it, outside the sandbox, after
  `leanchecker Janus` passed in a sandboxed, non-`--fresh` verification.
* **When it is read.** Once per verification, right after the framework build is pinned and
  before any untrusted step (the trusted compile, the proof compile, a consumer's Lake build) runs.
  Without a sandbox it is read too (the unconfined proof runs only after the decision, and the
  pins it covers are checked after every step as before), but never written; `--fresh` neither
  reads nor writes it. With a verdict, the framework modules of the theorem's closure count as
  replayed (reported as reused from the replay cache). Which modules qualify is decided by the
  same closure check as before: only `Janus.*` modules that the framework pins cover and that
  resolve from the pinned framework build. `Extracted`, `JanusTrusted`, the proof's own modules,
  consumer and dependency modules are never covered by it: they are replayed as before (or reused
  only through their own per-module markers, keyed by their own bytes).
* **Without a verdict** the framework is replayed alongside the other stages, as before. Concurrent
  verifications of a framework build that has no verdict yet serialise on a replay lock
  (`v1/replay/locks`): the first replays and records the verdict, the others then find it and do
  not replay (before, each started its own `leanchecker Janus`). A failing replay records nothing,
  and the regular replay then runs and reports leanchecker's error.
* **Eviction.** A verification that uses the verdict holds its use lock (`<key>.use`) shared until
  it ends; the collector removes a verdict only under that lock, taken exclusively without
  waiting. A removed verdict only makes the next verification replay the framework again.

What a verdict cannot do: make a module count as replayed whose bytes were not replayed (its key
covers every framework module-data file, and the pins are re-checked after the replay), outlive a
change of the framework or the toolchain, or cover a non-framework module. Its trust is the same
as that of the per-module markers it subsumes (the trusted cache is trusted), now additionally
authenticated against anything that can create files in the cache but cannot read the key.
`TestR1ForgedFrameworkLemma` and the audit row `R1b_forged_lemma` (a framework `.olean` carrying a
lemma the kernel never checked) are still rejected by the kernel replay: the forged bytes have
other pins, hence no verdict.

**What the replay does not cover, and what does.** A replay checks that a module is
*well-typed*, not that it is the module its source describes: an `.olean` compiled from a
modified framework source (say `Ensures := True`) replays fine. That is why the framework
build is also **pinned**: the SHA-256 of every framework `.olean` (and of the trusted
`Extracted`/`JanusTrusted`) is recorded right after the trusted build and re-verified after
every untrusted step (the proof compile, the consumer's Lake build and `lake query`), after the
audit and after the replay; untrusted build outputs (consumer and dependency modules, the proof)
are pinned once they are final, so the replay checks exactly the bytes the audit read. In a
consumer workspace the framework package is additionally **mounted read-only** for every
sandboxed process (a mount point cannot be renamed or removed from inside), and the
workspace's framework build is replaced from the trusted cache whenever it differs from the
pins. A changed, corrupted, missing or extra framework module is rejected (`framework
integrity`). See finding R1 in [docs/AUDIT.md](AUDIT.md).

**The ready stamp names the sources the build was compiled from** (round 10 F1). A build's stamp
records the framework's SHA-256 and the hash of every compiled module. A `--janus-root` checkout
is built in place, so after Lake runs janus reads the checkout's sources again and stamps the
build only if they still hash to the framework it started with (a cached copy is compared with the
framework's files again): otherwise a checkout that changed during the build (a `git checkout`
elsewhere) would leave modules of another commit stamped as this framework's, used by every later
run and reported under its SHA-256. Sources that change and change back within one build are not
detected.

**The compiled auditor.** `janus verify` runs the auditor as the executable `janus-audit`
(`lean_exe`, root `Janus.Tools.AuditMain`): the same `JanusAudit.runImpl` the `Audit.lean` script
calls, compiled by the Lean toolchain together with the framework build, outside the sandbox. Its
SHA-256 is part of the framework build's ready stamp (a changed executable makes the build "not
ready" and it is relinked) and it is hashed again right before it runs, with nothing untrusted
running between that check and its start. The Lean compiler that produced it is part of the
toolchain (item 5).

**The trusted-compile cache** (`v1/trusted`) holds compiled `Extracted`/`JanusTrusted` modules
keyed by the toolchain's identity, the framework build's pins and the two sources. Each entry has
a manifest with the SHA-256 of every file, checked on use, and an HMAC-SHA256 of the key and
those hashes under the result cache's private key (below). An entry whose manifest has no MAC or
a wrong one (planted, copied from another cache, or recorded before round 8) is a miss, and the
next compile replaces it (round 8 M1). Like the replay cache it is written only by janus outside
the sandbox, is read-only to sandboxed processes, and is off with `--fresh` and without a
sandbox.

**Toolchain identity.** Every cache key (replay, early replay, trusted compile, result) names
the toolchain by `cacheID`: its version string, the SHA-256 of `bin/lean` and `bin/leanchecker`,
and the path, size, modification and change times, inode, device and mode of every file under
the toolchain's `bin/` and `lib/lean/` (a symbolic link also by its target and the file it
names). `bin/lean` is a small launcher; the elaborator and the kernel are in
`lib/lean/libleanshared.so` and the core `.olean` files, so a toolchain rebuilt or patched in
place under the same version changes every key. Stat data, not content hashes, is used for the
library (about 15 000 files, 233 MB for `libleanshared.so` alone); a rewrite changes the change
time, which the writer cannot set back. A toolchain that cannot be walked gets a random identity,
so its caches always miss (round 8 L1).

**The cache root must be private** (round 8 C1). Before the cache is used, janus requires that
the cache root (`JANUS_CACHE_DIR`, else the user cache directory's `janus`), after resolving
symbolic links, is a directory owned by the current user and not writable by group or others,
and that each of its directories janus uses (`v1`, `v1/result`, `v1/trusted`, `v1/replay`,
`v1/framework`, `v1/consumer`, `v1/tmp`, `v1/run`) is a real directory (not a symbolic link)
with the same owner and mode restriction. Every ancestor of the root must be owned by the user
or by root, and not group- or other-writable unless it has the sticky bit (as `/tmp` has: others
cannot rename or remove our entries there). The result directory must be 0700 and its key
(`v1/result/.key`) a regular file owned by the user, of mode 0600 or stricter, not a link.
Cache files (entries, manifests, the key) are opened with `O_NOFOLLOW`. A violation stops
`janus verify` with an `Invalid` diagnostic (stage `cache safety`) naming the path and what is
wrong, never a silent miss: another user who can write the root could choose the key and forge a
`Cached: Verified` report, or plant a framework build or a trusted compile.

### Verification-result cache

A successful `janus verify` of a single proof file (not `--proof-root`) is recorded in
`v1/result`, and an identical later verification prints the recorded report, marked `Cached:`,
instead of compiling, auditing and replaying again. This makes the cache part of the trusted
base. What it relies on:

* **Key.** The SHA-256 of every input the outcome depends on: the janus executable itself (all
  verifier logic and the embedded framework), the framework (its sources' hash and source,
  the build directory, the SHA-256 of every compiled framework module and of the compiled
  auditor), the toolchain's identity (version, the SHA-256 of `lean` and `leanchecker`, and
  the metadata of every file under `bin/` and `lib/lean/`, `libleanshared.so` included: see
  "Toolchain identity" above), the sandbox mode, the theorem and options, the
  artifact, proof and binary paths, the bytes of `Extracted.lean` and `identity.json`, the
  binary's SHA-256 (verified against the binary by the same extraction check every run starts
  with) and the proof's bytes. A single-file proof can import only `Extracted`, the framework and
  Lean core, so these bytes are its whole import closure. The key is computed by the trusted
  process from bytes it reads itself, after the framework build is confirmed ready (stamped
  sources, pins, auditor); after a hit the inputs are read again and must be unchanged.
* **Authenticity.** Entries are written only by janus, outside the sandbox, after a successful,
  sandboxed, non-`--fresh` run, and each is authenticated with HMAC-SHA256 under a random 32-byte
  key created on first use (mode 0600, in the result directory, which must be private: see
  "The cache root must be private" above). The same key authenticates the trusted-compile
  manifests. An entry whose report or key does not verify is ignored: the verification runs.
* **Isolation.** The result directory, key included, is not visible to sandboxed code at all:
  bubblewrap and the unshare fallback mount an empty tmpfs over it (the unshare script stops if
  it cannot), on top of the read-only cache. A proof or a lakefile can neither read the key nor
  write an entry.
* **Bypass.** `--fresh`, `--unsafe-no-sandbox` and `JANUS_RESULT_CACHE=off` neither read nor
  write the cache. Without a sandbox the proof runs unconfined with the user's privileges, and
  anything it does to the cache (or to the replay and trusted-compile caches) is outside the
  threat model, as before; rerun with `--fresh` after running an untrusted proof unsandboxed.
* **Other users.** A cache root another user can write (a shared or group-writable directory,
  one created by someone else, a symbolic link among its directories) or a key others can read is
  refused (round 8 C1), so another account cannot plant entries or learn the key.
* **Threats out of scope.** Anything running as the same user outside the sandbox (an
  unsandboxed proof, other software of that user) can write the cache directly, and can also
  replace the framework build and the replay cache; the cache does not defend against it.

`audit/round7/run-cache.sh` (run by `audit/round7/run-round7.sh`) attacks the cache: a proof and a lakefile that look for the key and
the entries and try to plant one (bubblewrap and unshare), a tampered entry, an entry recorded
with a different framework (a source change), `--fresh` and `--unsafe-no-sandbox`.
`audit/round8/run-round8.sh` adds trusted-compile manifests with a missing or bad MAC, a
group-writable cache root, a symbolic link among the cache directories and a 0644 key, and runs
the unit rows for the toolchain identity. Every row must be blocked. There is no long-lived verification daemon (`janus serve`): docs/TESTING.md
explains why it would not pay for the trusted state it would add.

### Cache eviction

The cache collector (`janus cache gc`, and automatically after `verify`, `verify-batch` and
`blockers`; docs/CLI.md "Cache", `cmd/janus/cachegc.go`) deletes cache entries to keep the cache
within a size budget. It adds no trusted state, and it cannot make janus accept anything it would
not accept with an empty cache:

* **It only deletes.** It never writes an entry, a manifest, a stamp or the result key, and never
  renames anything except into its own fresh trash directory (`v1/tmp/gc-*`, removed at the end).
  `TestCacheGCRedTeam` checks that a collection creates nothing but its lock, that a dry run
  changes nothing, that the result key is untouched and that a forged result entry stays rejected.
* **Every reader already survives deletion.** Each cache is checked when it is read, so a missing
  entry is a miss and a partly missing one is a mismatch: a result or trusted-compile entry must
  carry a valid HMAC under the hidden key and match the SHA-256 of every file; the framework build
  is used only if its ready stamp, sources and module pins all match (otherwise it is rebuilt from
  the embedded sources); consumer workspaces are untrusted by design (their modules are rebuilt,
  pinned and kernel-replayed; the framework copy in them is pinned against the trusted build); a
  replay marker (and the framework replay verdict) only skips a replay whose module bytes and
  imports its name hashes, and only if its HMAC verifies, so deleting one only makes the replay
  run again; a verdict in use is held by its use lock and not collected. An evicted entry is rebuilt from the same inputs, and the
  rebuilt entry is equivalent: `TestCacheGCConcurrentVerify` empties the cache during and after
  verifications (single files and a consumer package) and gets the same theorem, statement,
  axioms and replay status.
* **Nothing in use is removed.** Entries with a lock are removed only under that lock, taken
  exclusively without waiting; an in-use workspace (exclusive), framework build (shared) or
  JanusASL build (`.use`, shared, held for as long as a verification uses it) is skipped. The
  entry is made unusable first (the framework's `.ready` stamp is removed), then renamed away in
  one step, and its lock files are removed while held: a process waiting on the old lock re-checks
  the inode (`lockFileMode`), takes the new lock and finds no entry, so it rebuilds. Lock-less
  entries are removed by one rename or unlink, and their writers publish them by one rename, so a
  reader sees a whole entry or none. Entries used within the grace period, and the builds the
  process uses, are kept besides (`TestCacheGCRespectsLocks`, `TestCacheGCConcurrentHolders`).
* **No symbolic link is followed.** Sizes are taken with `lstat`, entries are removed with
  `rename`/`unlink`/`RemoveAll`, none of which follow links: a link a consumer build plants in its
  (writable) workspace, or a link put in place of an entry, is removed itself, never its target.
* **Only a private cache is collected.** The collector runs the round-8 check (`checkCacheRoot`)
  first: in a cache another user can write, nothing is deleted (`janus cache gc` fails with
  `Stage: cache safety`), since such a cache is not ours and none of its entries are trusted.
* **What a red team could still do.** A process that can write the cache could plant entries,
  but that is the round-8 threat and outside the model with or without eviction. Deleting an
  entry can make the next run slower (a JanusASL build takes an hour) but never weaker: the
  verifier's checks on a rebuilt entry are the same as on a first build. Touching an entry's
  modification time (only possible for the consumer's own workspace, from inside the sandbox)
  only changes which entries the collector keeps.

**Not trusted:**

* The Go compiler and linker. We reason about their output.
* Any source-level reasoning about the Go program.
* The extractor's reachability analysis (`branch.go`). It decides only *which* functions to
  copy, by following direct branches (`B`, `BL`, `B.cond`, `CBZ`/`CBNZ`, `TBZ`/`TBNZ`). It never
  decides what an instruction means: Lean decodes every word again. If it misses a callee (for
  example through an indirect `BLR`), that code is absent, and the model faults with `noCode`
  when control reaches it. A missed callee can make a theorem unprovable. It cannot make a
  false theorem provable.

## The ASL corollary (`janus verify --asl`)

`--asl` adds a second, separate guarantee: the verified `Ensures` theorem, transferred to Arm's
ASL as translated to Lean (the JanusASL package, [docs/ASL.md](ASL.md)). Its statement is recorded
under `asl` in `verified.json`; it says that from every ASL state related to the Go call state
(`Rel`) under the Linux EL0 configuration (`LinuxEL0Config`), the ASL run of the extracted words
returns to the caller in a state related to one satisfying the ABI and the postcondition.

It is a corollary, not a new proof obligation: `Ensures.toASL` (kernel-checked, in JanusASL)
applied to the verified theorem, with its three facts about the program (every word `StepOK`,
untagged code and stubs) obtained from `JanusASL.Classify.covered Extracted.program = true`, which
the kernel decides by evaluation on the identity-checked program. The trusted auditor checks the
corollary's type is exactly that derivation from the verified theorem; no untrusted module may
declare a JanusASL, ArmASL, Sail or generated-module name; the corollary's whole closure,
the ArmASL model included, is kernel-replayed and its compiled modules are pinned.

It additionally trusts what [docs/ASL.md](ASL.md#trust-story) lists: Arm's ASL to Sail
(sail-arm), Sail's Lean backend with JanusASL's patches (checked against qemu and the C++ build
of the same Sail on a 583,756-case corpus, not proved), the slice and splices, the `janus_step`
harness and lean-sail. The ASL run fetches instructions with the program's own `fetch`, not the
ASL's translated fetch, and only returning runs are transferred. Neither the trusted base nor the
meaning of the main theorem changes: the ASL stage runs after it and cannot alter its result.

## What a theorem about `Returns` / `Ensures` says

`GoABI.Ensures p entry args pre post` means: for **every** admissible return address `ret`
(`GoABI.RetAddr p ret`: `ret` is 4-aligned, below `2^48`, outside every extracted code segment
and not a stub address) and **every** state `s` with `pc = entry`, `R30 = ret`, `Ri = args[i]`,
and `pre s` (all other registers, flags, `SP` and memory arbitrary), there exist a finite fuel
and a state `s'` such that `(p.withExit ret).run fuel s` returns `s'` (reaches `pc = ret`),
`s'` restores `SP`, `R28` (g), `R29` (FP) and `R18`, and `post s s'` holds. This is total
correctness: termination is part of the claim. Running out of fuel is not success, and neither
is any fault.

`p.run` itself never reports undefined behaviour. Every step either produces a state or a named
`Fault`. So `Returns` also rules out out-of-bounds or read-only memory accesses, misaligned
`SP`-based accesses, branches to code outside the extracted program, and unsupported
instructions on the paths taken from states satisfying `pre`.

### Outcome predicates

| Predicate | Meaning |
|---|---|
| `Returns p s post` | the run reaches `p.exitAddr` (for a call: `ret`) in a state satisfying `post` |
| `Panics p s` | the run reaches a Go panic stub (bounds check, divide by zero, explicit `panic`) |
| `Faults p s` | the run stops with a fault other than `outOfFuel` (a nil or out-of-bounds access, a read-only store, misaligned `SP`, a jump outside the code, an unsupported instruction) |
| `NeverPanics p s` | for every fuel: no panic stub **and** no fault; only `outOfFuel` is allowed (`neverPanics_iff : NeverPanics ↔ ¬ Panics ∧ ¬ Faults`) |
| `GrowsStack p s` | the run reaches `runtime.morestack*` |
| `Kernel.Traps p s` (`Amd64.Kernel.Traps`) | the run reaches a trap instruction (`BRK`, `UDF`; `INT3`, `UD2`, `HLT`): a `.trap` stub whose word is a trap, which executed faults with `Fault.trap` (`SIGTRAP`, `SIGILL`, `SIGSEGV`) |
| `Kernel.ReturnsK p E post onExit s k` | every run from `s` with kernel state `k` returns satisfying `post` (or ends the process with `exit_group`, satisfying `onExit`), where each system call, environment read and vDSO clock call has **any** result its contract allows (see "The kernel trust boundary") |
| `GoReturns p C s Q` / `EnsuresGo` | Go-level outcome (`Janus/GoABI.lean`): the run returns (`.returned s'`) or **panics with an interface value** (`.panicked v s'`: it stops at a panic stub, a faulting instruction or a frame exit that the classification `C` names, with the value `C` assigns); `Ensures.toGo` embeds every `Ensures` with no panic |

On real hardware every model fault is a crash or a Go panic: a memory fault is `SIGSEGV`, which
Go turns into `panic: runtime error: invalid memory address or nil pointer dereference`. So "never
panics" must exclude faults, and it does. `Returns` implies `NeverPanics`
(`Returns.neverPanics`), and `Faults`, `Panics` and `Returns` exclude each other.

`Faults` and `Panics` are positive claims about the model. A model fault means the code left the
memory, code and instruction subset the theorem grants; on hardware that access may hit another
mapping (memory the caller did not grant) rather than trap. Read `Faults` as "the function
needs more than the precondition provides", not as a guarantee of a hardware trap.

### The return address

A computed branch must never be mistaken for a return. The model ends a run when `pc` equals
`p.exitAddr`, and the extractor renders `exitAddr := 0`. If specifications used that fixed value,
any branch to 0 (a `BR` through a zero code pointer loaded from caller memory, a nil closure)
would "return", while on hardware it is a `SIGSEGV`. So specifications never use the extracted
value. `Ensures` (and every direct `Returns`/`Panics`/`NeverPanics` theorem in the examples)
quantifies over all `ret` with `RetAddr p ret` and runs `p.withExit ret` (`{ p with exitAddr :=
ret }`; the extracted `Program` itself is unchanged). The argument that this is sound:

* A real call is `BL entry` from a caller outside the extracted code. Its return address is the
  instruction after the `BL`, in the caller: 4-aligned, a user address below `2^48`, not inside
  an extracted segment, and not a runtime stub. So it satisfies `RetAddr`, and the theorem
  applies to it.
* The theorem holds for every such `ret`, with memory and registers otherwise as in `pre`. A
  path that reaches `ret` other than through the value the caller put in `X30` (a branch to a
  constant, or to a word loaded from memory that `pre` does not tie to `X30`) reaches it only for
  some values of `ret` and faults (`noCode`) for the others, so the theorem is not provable.
* Excluding the code ranges matters: if `ret` could be an address in the function, reaching that
  instruction in the normal course of execution would count as a return. Excluding stubs keeps
  `Panics` meaningful. The bound and the alignment are what `RET` itself needs (the model
  faults on misaligned or tagged branch targets).

Calls whose return address lies inside the extracted code (recursion, or a caller that was
extracted together with the callee) are not covered by the callee's theorem; they are covered by
the theorem about the outer function, which executes or summarises the inner call. Callee
summaries (`Tactic.Summary`) are stated on the extracted program and moved to `p.withExit ret`
by `Summary.withExit`, because their steps never touch `ret` (there is no code there).

## Assumptions and limits

A verified theorem is a statement about the following idealised execution. It says nothing
about executions outside it.

* **Single-threaded.** Memory changes only through the function's own stores. There are no
  other goroutines or OS threads, no concurrent writes and no weak-memory effects. Atomics and
  barriers mean only their sequential semantics: a load-acquire (`LDAR`, `LDAPR`, `LDAXR`) is
  an ordinary load, a store-release (`STLR`) an ordinary store, and the acquire/release
  variants of the LSE atomics behave like the plain ones. With one thread and no other
  observer these are equivalent; a theorem says nothing about what another thread would see.
  The one effect of the outside world a single thread can observe in its own registers, the
  outcome of a store-exclusive (an interrupt, an eviction or another observer can make it fail),
  is an input of the run (`State.exclPass`) that theorems quantify over.
  See "Atomics, exclusives and system registers" below.
* **No signals, no asynchronous preemption, no interrupts.** Go's signal-based async
  preemption, profiling signals and injected calls (`sigpanic`) are not modelled (except that a
  store-exclusive may fail at any time, which is how an interrupt would show up there).
* **No runtime interaction.** No GC (write barriers, stack scanning, moving stacks), no
  scheduler, no stack growth (calls into the runtime can be assumed as contracts instead of
  executed: see "Runtime contracts" below). Reaching `runtime.morestack*` ends the run as a `morestack`
  outcome, and it is not a return. Calls into other runtime functions only work if they were
  extracted and their code is in the supported subset. They then run in the same idealised
  model. Functions with a stack-check prologue need `GoABI.StackGuardOK s k` (g readable,
  `stackguard0 + k < SP`) for the prologue to fall through.
* **User mode only (EL0).** There are no system registers beyond NZCV and the read-only
  `DCZID_EL0` (`State.dczid`) and `TPIDR_EL0` (`State.tpidr`, see below), no exceptions and no
  page tables. `SP` alignment checking (SCTLR_EL1.SA0, as Linux configures it) is modelled as a
  fault. Other alignment faults are not modelled, except where the instruction model says so.
* **Memory outside the listed regions faults.** Every load and store must lie entirely inside
  one `Region` of `s.mem.regions` that ends at or below `2^48` (and a writable one, for stores).
  A store also faults if any byte it touches lies in a read-only region, even if a writable
  region covers it too: permissions are per byte on hardware, so overlapping regions cannot
  make read-only data (`DataLoaded`) writable. Otherwise the run faults.
  The `2^48` bound is the Linux arm64 user address limit (48-bit VA; a kernel with 52-bit VA
  only hands out higher addresses to `mmap` calls that ask for them, which Go does not). Every
  real call state has its memory below it, so it is representable. In exchange no successful
  access wraps around `2^64`, and no tagged address (top byte non-zero) is accessible, so the
  top-byte-ignore aliasing of Linux EL0 (`x` and `x + 2^56` naming the same byte) cannot occur
  in a proof: two accessible ranges that are `Disjoint` as numbers are disjoint in hardware. The
  same bound is used for amd64, where it is also sound (user addresses are below `2^47`, and
  `[2^47, 2^48)` is non-canonical; see `docs/AMD64.md`).
  A theorem therefore holds only for callers whose memory layout satisfies the regions stated
  in its precondition: the stack window (`StackWritable`), the argument/spill area above `SP`,
  the `g` struct, and every heap object the function touches. Real memory can have more mapped
  pages than the model allows, so the model is conservative. A program that reads an unlisted
  but mapped address on real hardware cannot be proved to return.
* **Code is not memory.** Instructions are fetched from the extracted segments, not from
  `s.mem`. Read-only constants the code loads (`.rodata`, literal pools) are copied by the
  extractor into `Program.data`; a theorem that needs them assumes `Program.DataLoaded`
  (memory holds exactly those bytes in a read-only region). Writable globals (`.data`,
  `.bss`, `.noptrdata`, `.noptrbss`) are never copied, because their contents are not fixed
  by the binary: a proof that touches one must list it as an ordinary region in its
  precondition. Self-modifying code is not modelled, and stores never change the fetched code.
* **The return address.** Specifications quantify over every admissible return address (see
  "The return address" above), so the extracted placeholder `exitAddr := 0` never matters. A
  theorem stated directly on `Extracted.program` (without `withExit` and a universally
  quantified `ret`) uses the placeholder and counts any branch to `0` as a return; such a
  statement says much less, and is visible as such in the printed statement.
* **ABIInternal only.** `GoABI` covers integer arguments and results in `R0`–`R15` and
  stack-assigned words from `8(RSP)`. The SIMD&FP registers are in the state (`State.vregs`,
  arbitrary in every call state, not preserved by `ABIReturn`: Go's ABIInternal has no
  callee-saved SIMD&FP registers). `CallSetup` passes no floating-point arguments or results
  (`F0`–`F15`, the low bits of `V0`–`V15`): a theorem about a `float64` function states them as
  preconditions on `s.getV i 64` and results on `s'.getV 0 64` (see "Floating point" below).
  "`R29` is preserved" relies on Go's frame-pointer convention (`GoABI.FPConvention`:
  `R29 = SP - 8` at the call), because Go 1.26 leaf functions restore `R29` arithmetically.
* **64-bit addresses as naturals.** Addresses are `Nat` values below `2^64`, produced by the
  instruction model's wrap-around arithmetic. Region bounds are compared in `Nat`, and every
  accessible byte is below `2^48`.
* **Fixed binary.** A theorem is about one binary, identified by SHA-256. Rebuilding with
  another compiler version, other flags or another linker layout invalidates it. `janus check`
  detects this.

## Atomics, exclusives and system registers

`sync/atomic` and the runtime compile to load-acquire/store-release, LSE atomics and
load/store-exclusive loops; `runtime.memclrNoHeapPointers` uses `DC ZVA` after reading
`DCZID_EL0`. The model covers them as follows (`Janus/Arm64/Decode.lean`, `Exec.lean`).

* **Ordered accesses** (`LDAR`, `LDAPR`, `STLR`, all sizes) are ordinary loads and stores in
  the single-threaded model. `LDLAR`/`STLLR` (FEAT_LOR) are rejected.
* **LSE atomics** (`LD<op>` for ADD, CLR, EOR, SET, SMAX, SMIN, UMAX, UMIN; `SWP`; `CAS`;
  `CASP`; every size and A/L variant; the `ST<op>` aliases) are one-instruction
  read-modify-writes. Single-threaded, they are deterministic and are modelled exactly: read
  the old value, write the new one, put the old one in the destination register. The access
  needs write permission even when `CAS` does not store. `CASP` with an odd register is
  rejected (UNDEFINED).
* **Alignment.** Ordered, exclusive and atomic accesses fault (`Fault.unaligned`) unless naturally
  aligned (`CASP`: to the pair). Hardware without FEAT_LSE2 always faults there; with FEAT_LSE2
  some of them succeed when they stay inside 16 bytes. The model is conservative for both.
* **Feature assumptions.** Accepting an instruction means assuming the CPU implements it: the
  model is of a CPU with FEAT_LSE (`LD<op>`, `SWP`, `CAS`, `CASP`) and FEAT_LRCPC (`LDAPR`).
  On an Armv8.0 CPU they are UNDEFINED (`SIGILL`). Go code does not depend on this blindly: it
  runs LSE instructions only after testing `runtime.arm64HasATOMICS`, a byte the runtime sets
  at start-up from the CPU's capabilities (or, built with `GOARM64=v8.1`, it refuses to start
  without LSE). A proof through such a test assumes the flag in its precondition, as
  `examples/proofs/AtomicAdd.lean` does, and on a CPU without LSE that precondition is false,
  so the theorem is vacuous there rather than wrong. A proof about code that uses LSE
  unconditionally is a statement about LSE-capable CPUs.
* **The `arm64HasATOMICS` precondition trusts the kernel.** The runtime sets the flag from the
  `HWCAP_ATOMICS` bit Linux reports in the auxiliary vector, so the precondition is "the kernel
  says every core has LSE". A kernel that over-reports a feature on a heterogeneous
  (big.LITTLE) system — as happened with atomics, Go issue 28431 — makes the precondition true
  on a CPU where an LSE instruction can trap; the theorem is then about a machine that is not
  the one running. The same holds for any other HWCAP-derived flag a proof assumes.
* **FP/AdvSIMD.** FEAT_FP and FEAT_AdvSIMD are formally optional in Armv8-A, yet the model
  accepts Advanced SIMD instructions and SIMD&FP loads/stores and moves unconditionally (see
  "Advanced SIMD" below), and Go uses them unguarded (`memequal`, `IndexByte`, large copies).
  Accepting them assumes the CPU implements both; every system that runs Go's arm64 port does
  (the AArch64 procedure-call standard passes floating-point values in SIMD&FP registers).
  FEAT_AES, FEAT_LRCPC and FEAT_LSE are assumed in the same way where their instructions are
  accepted, and so are FEAT_SHA1, FEAT_SHA256, FEAT_SHA512, FEAT_SHA3, FEAT_PMULL and FEAT_CRC32
  (see "Crypto extension, CRC32, permutes" below).
* **Exclusives: the monitor and the environment's choice.** `LDXR`, `LDAXR`, `LDXP`, `LDAXP`
  (every size) are aligned loads that mark the *local exclusive monitor*, `State.excl :=
  some (addr, size)` (Arm ARM B2.9, `AArch64.SetExclusiveMonitors`). `STXR`, `STLXR`, `STXP`,
  `STLXP` (every size) write their status register as the pseudocode does
  (`if AArch64.ExclusiveMonitorsPass(address, dbytes) then Mem[address] = data; status = '0'
  else status = '1'`), with `ExclusiveMonitorsPass` modelled as follows (`Exec.lean`, "The
  exclusive monitor"):
  * **Open Access state** (`excl = none`): the store-exclusive **fails**: status 1, nothing is
    written. This is the one outcome the architecture guarantees (`IsExclusiveLocal` is FALSE
    when nothing is marked); the monitor is open after `CLREX`, after every store-exclusive to
    the marked bytes, and (for the oracle) at the start of a case.
  * **The marked bytes**: the store-exclusive **may** pass, never must. Hardware may clear the
    monitor at any moment, even with one thread (an interrupt or exception return, a context
    switch, a cache eviction, the global monitor, a store by this PE to the marked bytes, an
    IMPLEMENTATION DEFINED event), so a *spurious failure* is always allowed. The outcome is
    therefore not computed but read from the environment: `State.exclPass 0` (true = pass),
    after which the stream advances by one and the monitor is open. A theorem about arbitrary
    initial states quantifies over `exclPass`, so it holds for **every** sequence of outcomes;
    the model never assumes a pass.
  * **Other bytes** (a store-exclusive whose address or size differs from the marked ones):
    whether it passes is IMPLEMENTATION DEFINED (the marked region may be a whole reservation
    granule) or CONSTRAINED UNPREDICTABLE, and so is whether it clears the monitor. The model
    does not pick an answer: the run stops with `Fault.unpredictable`. Go's LL/SC loops and the C
    outline atomics always store to the bytes they loaded, so this costs no coverage.
  * **Faults first.** The alignment check (always: the model is conservative about FEAT_LSE2, as
    for the other exclusive and atomic accesses) and the memory permission check of the store
    come before the monitor. The Arm ARM leaves it IMPLEMENTATION DEFINED whether memory aborts
    are detected before the monitor check, so on hardware a failing store-exclusive to an
    inaccessible address may return status 1 instead of faulting; the model faults (it never
    claims the status-1 result there).
  * **What is not modelled, and why that is sound.** Ordinary stores do not clear the model's
    mark (on hardware it is IMPLEMENTATION DEFINED); keeping the mark only permits a pass that
    hardware might not give, and every pass is the environment's choice anyway. The global
    monitor, other observers and the ordering effects of the acquire/release forms are outside
    the single-threaded model, as for every other instruction. `ExclusiveMonitorsStatus()`
    returns 0 after a passing store (it returns 1 only if the translation of the address changed
    between the check and the write, which cannot happen within one instruction here).
  * **Why this covers every hardware run.** Take the model's initial `excl` to be the hardware
    monitor's state at the call (`none` if open, `some m` if it marks the bytes `m`) and
    `exclPass` to be the outcomes the hardware's store-exclusives to the marked bytes actually
    have. Then at every step, `excl = none` implies the hardware monitor is open, and
    `excl = some m` implies it is open or marks exactly `m` (a load-exclusive marks the same bytes
    on both; `CLREX` opens both; the hardware may open its monitor at any time, which the model
    does not need to follow; a store-exclusive to `m` opens it, since `IsExclusiveVA` may return
    FALSE only outside the marked region and `ClearExclusiveLocal` is then reached). Under this
    invariant every hardware store-exclusive outcome is the model's (a fail in the Open state, the
    stream's outcome on `m`), or the model stops (`unpredictable`, a fault). A theorem about
    arbitrary initial states covers this initial state, hence the hardware run. A theorem whose
    precondition restricts `s.excl` or `s.exclPass` says so in its printed statement.
* **Retry loops terminate only under a stated progress hypothesis.** An LL/SC loop
  (`LDAXR`; compute; `STLXR`; `CBNZ` back) returns once a store-exclusive passes, and under the
  all-fail stream it never does. Its theorem must therefore assume eventual success explicitly,
  as a precondition on the initial state: `∃ k, s.exclPass k = true` (the `k+1`-th
  store-exclusive to the marked bytes passes). This is the forward-progress property the Arm ARM
  describes for such loops (an exclusive pair with no other explicit memory access, cache
  maintenance or `CLREX` in between, a few instructions apart); the model does not assume it, the
  theorem states it. `examples/proofs/AtomicAdd.lean` (`anyCPU`) proves `atomic.AddUint64`
  through both paths: the LSE `LDADDAL` when `runtime.arm64HasATOMICS` is set, and otherwise the
  LL/SC loop under this hypothesis (`loop`: by induction on the index of the first pass; a failed
  attempt returns to the loop head with memory unchanged and the stream advanced). A safety
  property that needs no hypothesis (the loop never faults, whatever the outcomes) is true but
  not stated as a theorem there.
* **PRFM/PRFUM** (all forms and prefetch operations) only advance `pc`: a prefetch never faults
  and has no architectural effect.
* **`DCZID_EL0` is a parameter, not a constant.** `MRS Xt, DCZID_EL0` (the only accepted system
  register read) returns `State.dczid`, the five meaningful bits (`DZP`, `BS`). The value is
  IMPLEMENTATION DEFINED (qemu `-cpu max` reports 7, i.e. 512-byte blocks; the Sail Armv9.4
  model 8; many Neoverse cores 4), so it lives in the state, execution never changes it, and a
  theorem about arbitrary initial states quantifies over all 32 values. A proof may restrict
  it by a visible precondition. `DC ZVA, Xt` zeroes the naturally aligned block of
  `4 << BS` bytes containing `Xt` (checked as a store of that many bytes) and faults
  (`Fault.trapped`, `SIGILL` on Linux) when `DZP = 1`. Other `DC`/`IC`/`SYS` operations are
  rejected. `examples/proofs/ClearWords.lean` proves `runtime.memclrNoHeapPointers` (through its
  `DC ZVA` path) for every value of `DCZID_EL0`.
* **`DCZID_EL0` is assumed uniform across cores.** `State.dczid` is one value for the whole run,
  but the register is IMPLEMENTATION DEFINED *per core*. Go reads it once and caches the block
  size; a thread that migrates to a core with a different `BS` between that read and `DC ZVA`
  zeroes a different block size than the code planned for. A theorem that reads `DCZID_EL0`
  (ClearWords) is therefore about systems whose cores all report the same value; no shipping
  heterogeneous system is known to differ, but the architecture does not forbid it.
* **`TPIDR_EL0` is a parameter too.** `MRS Xt, TPIDR_EL0` (the thread pointer; Go's runtime reads
  it in `save_g`/`load_g` under cgo) returns `State.tpidr`. Linux gives each thread its own
  value and EL0 code may write it, but no instruction the model accepts does (`MSR TPIDR_EL0` is
  rejected), so within a run it is a constant of the state and theorems quantify over it.

## Advanced SIMD

`State.vregs` holds `V0`–`V31` (128 bits each); the Advanced SIMD operations are in
`Janus/Arm64/Vector.lean`, transcribed from the ASL `Operation` pseudocode (element loops become
`ofElems`, `Elem[x, e, esize]` is `elem x esize e`). Covered:

* **Loads and stores:** `LDR`/`STR`/`LDUR`/`STUR` (all addressing modes) and `LDR` (literal) of
  B/H/S/D/Q registers, `LDP`/`STP` of S/D/Q registers, `LD1`/`ST1` (multiple structures, 1–4
  registers), `LD1`–`LD4`/`ST1`–`ST4` (single structure) and `LD1R`–`LD4R`, with every
  post-index form. Rejected: `LD2`–`LD4`/`ST2`–`ST4` (multiple structures), `LDNP`/`STNP`,
  `LDAPUR`/`STLUR` and every reserved size. Each register (multiple structures, pairs) or element
  (single structure) is a checked access as in the pseudocode; a fault anywhere faults the whole
  instruction.
* **Integer data processing:** the three-same logical operations (`AND`, `BIC`, `ORR`, `ORN`,
  `EOR`, `BSL`, `BIT`, `BIF`), `ADD`/`SUB`, the compares (`CMEQ`, `CMTST`, `CMHI`, `CMHS`,
  `CMGT`, `CMGE`, and against zero `CMEQ`/`CMGE`/`CMGT`/`CMLE`/`CMLT`), `SMAX`/`UMAX`/`SMIN`/`UMIN`
  and their pairwise forms, `ADDP`; scalar `ADD`/`SUB`/compares on D registers; across lanes
  `ADDV`, `SADDLV`/`UADDLV`, `SMAXV`/`UMAXV`/`SMINV`/`UMINV`; `CNT`, `NOT`, `RBIT`,
  `REV16`/`REV32`/`REV64`, `ABS`, `NEG`, `XTN`; shifts by immediate `SSHR`/`USHR`, `SSRA`/`USRA`,
  `SHL`, `SLI`, `SRI`, `SHRN`, `SSHLL`/`USHLL`; `MOVI`/`MVNI`/`ORR`/`BIC` (immediate) and `FMOV`
  (vector, immediate: a fixed bit pattern); `EXT`, `TBL`/`TBX`.
* **Moves:** `DUP` (element, general), `INS` (element, general), `UMOV`, `SMOV`, and `FMOV`
  between general and SIMD&FP registers (`Wn`↔`Sd`, `Xn`↔`Dd`, `Xn`↔`Vd.D[1]`).
* **AES:** `AESE`, `AESD`, `AESMC`, `AESIMC`, with the S-boxes and row permutations copied from the
  ASL and GF(2^8) multiplication checked against the ASL tables (`JanusTests/Vector.lean`).
  Accepting them assumes FEAT_AES; Go only runs its AES hash after testing `cpu.ARM64.HasAES`
  (`runtime.useAeshash`), so a proof through it assumes that flag, as for LSE.

* **The rest of Advanced SIMD** (`Janus.Arm64.NeonInstr`, decoded by `decodeNeon` for the
  words the classes above reject, executed by `execNeon`; the lane operations in
  `Janus/Arm64/Neon.lean` and `NeonFP.lean`, transcribed statement by statement from the
  `decode` and `Operation` ASL of sail-arm's `instrs64.sail`, with element-size generic helpers
  so one definition covers every arrangement and the scalar forms):
  * every integer opcode of three same (halving, saturating, rounding and saturating shifts by
    register, `SABD`/`UABD`/`SABA`/`UABA`, `MLA`/`MLS`, `MUL`/`PMUL`, `SQDMULH`/`SQRDMULH`), three
    different (`SADDL`…`USUBW`, `ADDHN`/`RADDHN`/`SUBHN`/`RSUBHN`, `SABAL`/`SABDL`, `SMLAL`/`UMLAL`/
    `SMLSL`/`UMLSL`, `SMULL`/`UMULL`, `SQDMLAL`/`SQDMLSL`/`SQDMULL`), two-register miscellaneous
    (`SADDLP`/`UADDLP`/`SADALP`/`UADALP`, `SUQADD`/`USQADD`, `CLS`/`CLZ`, `SQABS`/`SQNEG`,
    `SQXTN`/`UQXTN`/`SQXTUN`, `SHLL`), shift by immediate (`SRSHR`/`URSHR`, `SRSRA`/`URSRA`,
    `SQSHLU`, `SQSHL`/`UQSHL`, `RSHRN`, `SQ(R)SHR(U)N`/`UQ(R)SHRN`), by element (`MUL`, `MLA`,
    `MLS`, the long and the saturating doubling forms), and their scalar forms; scalar `ADDP`
    (the permutes `UZP1/2`, `TRN1/2`, `ZIP1/2` and scalar `DUP` are `CryptoInstr.permute` /
    `dupScalar`, above);
  * single- and double-precision floating point on every lane, through the scalar ASL library
    (`FP.fpAdd`, `FP.fpMulAdd`, ... with the same `FPCR`, including `FZ`, `DN`, `FIZ` and `AH`),
    plus `FPCompareEQ/GE/GT`, `FPMulX`, `FPRecipStepFused`/`FPRSqrtStepFused`, the estimates
    `FPRecipEstimate`/`FPRSqrtEstimate`/`FPRecpX`/`URECPE`/`URSQRTE`, round-to-odd `FCVTXN`,
    `FPToFixed`/`FixedToFP` with fraction bits, and the halving tree of `Reduce` for `FMAXV`,
    `FMINV`, `FMAXNMV`, `FMINNMV` and the scalar pairwise forms: `FADD`…`FDIV`, `FMLA`/`FMLS`
    (vector and by element), `FMULX`, `FABD`, `FMAX(NM)(P)`/`FMIN(NM)(P)`, `FADDP`, the compares
    (also against zero and absolute), `FABS`/`FNEG`/`FSQRT`, `FRINT*`, `FCVT{N,P,M,Z,A}{S,U}`,
    `SCVTF`/`UCVTF` (also with fraction bits, vector and scalar, and the general-register
    fixed-point forms), `FCVTL`/`FCVTN` between single and double, `FRECPS`/`FRSQRTS`. A lane
    exception whose trap is enabled faults (`fpTrapped`); otherwise the lanes' exceptions are ORed
    into `FPSR`. The scalar forms merge into the upper part of the destination under
    `FPCR.NEP`, with the source register each ASL `execute` names;
  * `LD2`–`LD4`/`ST2`–`ST4` (multiple structures, every arrangement and post-index form),
    checked as one access of the whole interleaved block (never more permissive than the ASL's
    element accesses), and `LDNP`/`STNP` of S/D/Q registers (`LDP`/`STP` without writeback).

  Saturation sets `FPSR.QC` (bit 27). Two corners are IMPLEMENTATION DEFINED or differ between
  the references, so the model faults (`trapped`) instead of choosing: the single-precision
  `FRECPE`/`FRSQRTE` under `FPCR.AH = 1` (FEAT_RPRES changes their precision), and the vector
  `FABS`/`FNEG` under `FPCR.AH = 1` with a NaN lane (the ASL, and Sail, leave the NaN unchanged;
  qemu 10.2.1 changes its sign bit).

Not modelled, and rejected: half precision (FEAT_FP16, and the `FCVTL`/`FCVTN` forms to and from
half precision), BFloat16, dot products (FEAT_DotProd, FEAT_I8MM), `SQRDMLAH`/`SQRDMLSH`
(FEAT_RDM), `FMLAL`/`FMLSL` (FEAT_FHM), `FCMLA`/`FCADD`, `FRINT32*`/`FRINT64*`, SM3/SM4,
SVE and SME. An Advanced SIMD write sets the whole
128-bit register (`V[d, n] = x` zero-extends); on a CPU with SVE the hardware also zeroes the
upper bits of `Z[d]`, which are not part of the model and not observable by the accepted
instructions.

## Crypto extension, CRC32, permutes

`Janus/Arm64/Crypto.lean` transcribes the ASL of these instructions statement by statement
(the Sail translation of Arm's Armv9.4-A ASL, sail-arm `f5bf6c3`: the `execute_*` functions of
`instrs64.sail` and the shared `SHAchoose`, `SHAparity`, `SHAmajority`, `SHAhashSIGMA0/1`,
`SHA256hash`, `ROL`, `ROR`, `PolynomialMult`, `BitReverse`, `Poly32Mod2`); `ExecCrypto.lean` does
the register reads and writes, `DecodeCrypto.lean` the decoding (one hook each in `Decode.lean` and
`Exec.lean`, constructor `Instr.crypto`). Covered: `SHA1C`/`SHA1P`/`SHA1M`/`SHA1H`/`SHA1SU0`/
`SHA1SU1`, `SHA256H`/`SHA256H2`/`SHA256SU0`/`SHA256SU1`, `SHA512H`/`SHA512H2`/`SHA512SU0`/
`SHA512SU1`, `EOR3`/`RAX1`/`XAR`/`BCAX`, `PMULL`/`PMULL2` (8B→8H and 1D→1Q), `CRC32B/H/W/X` and
`CRC32CB/H/W/X`, the permutes `ZIP1`/`ZIP2`/`UZP1`/`UZP2`/`TRN1`/`TRN2` (every arrangement) and
`DUP` (element, scalar form, alias `MOV Sd, Vn.S[i]`). Rejected: SM3/SM4 and every unallocated or
UNDEFINED encoding of these classes (PMULL `size` 01/10, permute `size:Q = 110`, scalar DUP with
`imm5<3:0> = 0000`, CRC32 with `sf` not matching `sz = 11`).

Accepting them assumes the optional features FEAT_SHA1, FEAT_SHA256, FEAT_SHA512, FEAT_SHA3,
FEAT_PMULL and FEAT_CRC32 (and FEAT_AES above). Go runs these kernels only after testing the
matching `cpu.ARM64.Has*` flag (`HasSHA1`, `HasSHA2`, `HasSHA512`, `HasSHA3`, `HasPMULL`,
`HasCRC32`), so a proof through one of them states what the program assumed. On a CPU without
the feature the instruction is UNDEFINED (`SIGILL`) and such a theorem says nothing about that
CPU.

Proved on top (not trusted): `crc32Op_eq_update` (`Janus/Arm64/CryptoLemmas.lean`) shows that the
ASL formulation of CRC32/CRC32C (bit-reversed operands, `Poly32Mod2`, bit-reversed result)
equals the bytewise reflected CRC of RFC 1952 / RFC 3720 for every input, which the
`A64Crc32` example uses.

Go 1.26's `runtime.memmove`, `runtime.memclrNoHeapPointers` and the compiler's inline copies of
small values use general-purpose `LDP`/`STP`; larger copies (`LDP`/`STP Q16, Q17`), the
`internal/bytealg` routines (`memequal`, `IndexByte`, `Count`, ...), `aeshashbody` and
`internal/chacha8rand.block` use the instructions above.

## SSE packed instructions (amd64)

The legacy-SSE packed instructions of WP-D (`Janus/Amd64/InstrSSE.lean`, `DecodeSSE.lean`,
`ExecSSE.lean`) are part of the trusted amd64 model, like `Decode.lean` and `Exec.lean`: they
are written from the Intel SDM `Operation` sections and differentially tested on the host CPU
(`scripts/oracle-amd64.sh sse`, docs/ORACLE-AMD64.md: 0 MISMATCH), not proved. What a theorem
relies on beyond the SDM text:

* **CPU features.** The model executes SSE3, SSSE3, SSE4.1 and SSE4.2 instructions whenever they
  occur, as the host (and every amd64 CPU Go 1.26 runs on with `GOAMD64=v2` or later) does. On a
  `GOAMD64=v1` CPU without them they are `#UD`; Go's runtime and assembly test `internal/cpu`
  flags before using them, so a theorem about such a path holds on CPUs with the feature, and a
  proof that a guarded path is not taken states the flag.
* **Alignment.** A 128-bit legacy-SSE memory operand faults unless 16-aligned, except for the
  SSE4.2 string compares; the narrower operands never fault for alignment. The oracle steers
  both aligned and misaligned operands and agrees on every case.
* **Rejected rather than guessed:** implementation-specific results (`RCPPS`, `RSQRTPS`), the
  masked-off-byte behaviour of `MASKMOVDQU`, reserved immediate bits (`CMPPS/PD imm8 ≥ 8`,
  `ROUNDPS/PD imm8 ≥ 16`, `PCMPxSTRx imm8<7>`), `66` with `F2`/`F3` except on the 16-bit
  `CRC32`, MMX forms.
* **Proof automation** (`TacticSSE`) is not trusted: its element lemmas are proved from
  `ExecSSE`, and making `ExecSSE.crc32c` irreducible for the elaborator changes no definition.

## x86 crypto extensions (amd64)

AES-NI, `PCLMULQDQ`, SHA-NI and ADX (WP-E, `Janus/Amd64/InstrCrypto.lean`, `DecodeCrypto.lean`,
`ExecCrypto.lean`) are part of the trusted amd64 model. They are written from the Intel SDM
`Operation` sections and differentially tested on the host CPU, which has all four features
(`scripts/oracle-amd64.sh crypto`, docs/ORACLE-AMD64.md: 0 MISMATCH). What a theorem relies on:

* **CPU features (assumed).** The model executes these instructions whenever they occur, as a CPU
  with AES-NI, PCLMULQDQ, SHA-NI and ADX does; on a CPU without one of them they are `#UD`, which
  the model does not represent. Go tests `internal/cpu` before using them, and the theorems state
  the guard where the code tests it: `Memhash64`/`Memhash32` are stated for both values of
  `runtime.useAeshash` and `AddMulVVWW` for both values of `math/big.hasADX` (each path). A theorem about a
  function that does not test the flag itself (`encryptBlockAsm`, called by `crypto/aes` only
  after `supportsAES`) holds on CPUs with the feature.
* **The AES specification is independent.** `Janus/Spec/AES.lean` defines FIPS-197 (S-box from
  the GF(2^8) inverse and the affine map, `ShiftRows`/`MixColumns` by their formulas, `KeyExpansion`,
  `Cipher`) without the model's tables and proves the model's instructions equal to it; the
  appendix C vectors are checked by the kernel. A statement about AES therefore trusts FIPS-197 as
  transcribed there, not the ISA model's S-box table.
* **Rejected rather than guessed:** `66` together with `F2`/`F3` (hardware runs `66 F3 0F 38 F6`;
  the model refuses it), the other mandatory prefixes of each opcode, `LOCK`, and the VEX forms.
* **Proof automation** (`TacticCrypto`) is not trusted; its lemmas are proved from `ExecCrypto`.
  Passing the operand-address function to `ExecSSE.exec`/`ExecCrypto.exec` as the definition
  `eaNat s next` instead of a lambda changes no semantics (`eaNat s next a = (ea s next a).toNat`
  by `rfl`).
## AVX, AVX2, FMA3 and F16C (amd64)

The VEX-encoded instructions of WP-F (`Janus/Amd64/InstrAVX.lean`, `DecodeAVX.lean`,
`ExecAVX.lean`) are part of the trusted amd64 model too: written from the Intel SDM `Operation`
sections on top of WP-D's lane operations and differentially tested on the host CPU (an AVX2,
FMA, F16C and AVX-512 machine; `scripts/oracle-amd64.sh avx`, docs/ORACLE-AMD64.md: 0 MISMATCH),
not proved. What a theorem relies on beyond the SDM text:

* **YMM state.** `State.ymmHi` holds bits 255:128 of `YMM0`–`YMM15`; a VEX.128 register write
  zeroes it for the destination and a legacy-SSE write leaves it alone. Both are theorems about
  the model (`Janus.Amd64.Tactic.exec_vex128_zero_upper`, `exec_sse_preserves_upper`), and the
  native oracle compares all sixteen upper halves on every case (they start nonzero in most
  states). Since WP-G the AVX-512 state is modelled too (below): a VEX write also zeroes bits
  511:256 of its destination (`exec_avx_zero_zmm`), as the hardware does up to its `MAX_VL`.
* **CPU features.** VEX instructions execute whenever they occur; the model assumes AVX, AVX2,
  FMA and F16C (every x86-64-v3 CPU). Go code reaches them only behind `internal/cpu` flags or
  with `GOAMD64=v3`; C compiled with `-march=x86-64-v3` requires such a CPU.
* **Masked moves and gathers.** The model accesses (and checks) only the elements whose mask bit
  is set, as the SDM states; it additionally faults unless a masked move's whole operand is below
  `2^47`, which is stricter than hardware (the oracle shows a non-canonical, all-masked-off
  `VMASKMOVPD` store completing on the host; the model's fault there is a gap, not a mismatch).
  A gather that faults writes nothing in the model, while hardware has completed and cleared the
  elements before the faulting one; this partial state is visible only to a signal handler, and a
  fault ends every Janus execution. The native harness single-steps with `TF`: a gather that
  faults on a later element after loading earlier ones delivers the pending single-step trap
  instead, with `RIP` still at the gather and the elements done so far written (SDM:
  "Gathers ... can be suspended by an exception"); the oracle records that as a host success at
  `RIP = TestPC`, and the model's fault as a gap.
* **Rejected rather than guessed:** the implementation-specific approximations
  (`VRCPPS`/`VRSQRTPS` and their scalar forms), `VDPPS`/`VDPPD`, `VMASKMOVDQU`, `VLDMXCSR`,
  reserved immediates (`VCMP imm8 ≥ 32`, `VROUND imm8 ≥ 16`, `VPCMPxSTRx imm8<7>`), `VEX.L1` on
  the `LIG` scalar forms (hardware ignores it; no compiler emits it), every `W0`/`W1` field set
  the other way, and gathers with equal destination, index and mask registers (`#UD`).
* **Packed FMA.** An element whose result the manuals leave to the implementation (two or three
  NaN operands, `0 × ∞ + NaN`) makes the instruction `undefinedResult`, as for the scalar forms;
  a proof that uses a packed FMA must show no element is such a case.
* **Proof automation** (`TacticAVX2`) is not trusted: the compatibility lemmas with WP-D
  (`pintV_128`, `cvtV_128`, `vcmp_legacy`), the zero-upper theorems and the 256-bit element lemmas
  are proved from `ExecAVX`.

## AVX-512 (amd64)

The EVEX-encoded instructions of WP-G (`Janus/Amd64/InstrEVEX.lean`, `DecodeEVEX.lean`,
`ExecEVEX.lean`), the VEX opmask instructions and the VEX forms of `VPCLMULQDQ` and GFNI are part
of the trusted amd64 model: written from the Intel SDM `Operation` sections, reusing WP-D's lane
operations and WP-F's width-generic ones (`ExecAVX.perLane` now covers four 128-bit lanes), and
differentially tested on the host CPU (an Intel Xeon Gold 5412U, Sapphire Rapids, natively;
`scripts/oracle-amd64.sh avx512`, docs/ORACLE-AMD64.md: 0 MISMATCH), not proved. What a theorem
relies on beyond the SDM text:

* **State.** `State.zmmHi` holds bits 511:256 of `ZMM0`–`ZMM31`, and `xmm`/`ymmHi` at indices
  16–31 are the low halves of `ZMM16`–`ZMM31`; `State.kreg` the opmask registers `K0`–`K7`.
  An EVEX write of `l` bits zeroes bits 511:`l` (`exec_evex_zero_upper`), a VEX write bits
  511:`VL` (`exec_avx_zero_zmm`), legacy SSE changes none of it (`exec_sse_preserves_avx512`), and
  `VZEROUPPER`/`VZEROALL` act on `ZMM0`–`ZMM15` only. The native oracle loads every case's
  `ZMM0`–`ZMM31` and `K0`–`K7` (random, mostly nonzero) and compares them from the signal frame's
  XSAVE components.
* **The earlier models are unchanged** (`sse_compat`, `avx_compat`): with the AVX-512 state
  erased, the result of every WP-D and WP-F instruction is what it was before WP-G (the result
  from the state without AVX-512 state).
* **Calls clobber the AVX-512 state.** Every trusted call contract that lets a callee return
  leaves bits 511:256 of the `ZMM` registers and `K0`–`K7` unspecified (two existentials): both
  Go ABIs treat them as scratch, and the runtime does use them (the GC's span scanner writes
  `Z1`–`Z4` and `K1`). On the integration of wave 1 that is every amd64 call-return contract:
  `GoABI0.Ret0`, `FFI.GoResume` and `CbResume` (cgo and callbacks), the map, interface and
  allocation contracts, the equality/hash/typed-memory returns (`MemAmd64.retState`: `EqRet`,
  `IfaceRet`, `TRet`, `HRet`), `cmpstring` (`CmpRet64`), the string/slice specs (`RtPost64`), the
  write barrier (`WbContract64`), the panic runtime (`PanicRet`), the remaining runtime
  (`RTReturn64` of the instrumentation calls, the size-specialised allocator through `AllocRet64`,
  the soft-float leaf `LeafRet64`) and the kernel's vDSO clock calls (`Site.timeNow`,
  `Site.nanotime`). The C ABI's `CReturn` and the libc contracts state only what a C callee
  preserves, so the AVX-512 state is unspecified there already. `_cgo_topofstack`
  (`TopOfStack`, a few Go assembly instructions) keeps it.
* **CPU features.** EVEX and opmask instructions execute whenever they occur: the model assumes
  AVX512F, AVX512BW, AVX512DQ, AVX512VL, AVX512VBMI (`VPERMB`, `VPERMI2B`, `VPERMT2B`),
  AVX512VBMI2 (`VPCOMPRESSB/W`, `VPEXPANDB/W`), AVX512_BITALG (`VPOPCNTB/W`),
  AVX512_VPOPCNTDQ, GFNI and VPCLMULQDQ, with the OS enabling the opmask and ZMM state (XCR0 bits
  5–7). Go's runtime and `hash/crc32` reach them only behind `internal/cpu` flags; a theorem about
  such a path holds on CPUs with the features (every Intel Ice Lake / Sapphire Rapids server and
  AMD Zen 4 or later).
* **Fault suppression.** A full-width memory operand of an element-wise instruction under a write
  mask (the moves, the integer and bitwise arithmetic, `VPTERNLOG`, the variable shifts and
  rotates, `VPOPCNT*`, the compares, `VPBLENDM*`, the floating-point arithmetic: exception classes
  `E1`, `E2`, `E4`) accesses only its selected elements; masked-off elements are not checked and
  cannot fault, as the SDM specifies and the oracle confirms with operands that straddle the end of
  the buffer. Every other memory operand (the `E4NF`/`E6NF` classes: permutes, shuffles, GFNI,
  `VPCLMULQDQ`, inserts, extracts, broadcasts, `VPMOVSX/ZX`, and every broadcast element) is
  checked in full, which is at least as strict as hardware where the SDM class was not certain.
  The model also faults unless a masked operand lies below `2^47`, and checks the alignment of
  `VMOVDQA32/64`/`VMOVAPS/PD` whatever the mask; both are stricter than the host, which completes
  a masked misaligned aligned-move (model gaps, not mismatches).
* **Embedded rounding and SAE.** `{er}` replaces `MXCSR.RC` and, like `{sae}`, suppresses every
  floating-point exception (no `MXCSR` flags, no `#XM`); `DAZ`/`FTZ` still apply. Masked-off
  elements raise no exception.
* **Rejected rather than guessed:** `{z}` without a mask register, `{z}` with a memory
  destination, a mask on the instructions without one, `EVEX.b` on register forms other than the
  floating-point ones, `EVEX.L'L = 11`, the APX/reserved prefix bits, maps other than 1–3,
  any legacy prefix before `62`, and every opcode outside the decoded set (the scalar EVEX forms,
  conversions, `VPCONFLICT`, `VPLZCNT`, gathers/scatters, FP16, `VNNI`, `IFMA`). The oracle found
  three encodings the decoder had first rejected and hardware accepts: `VEX.B` set on an opmask
  `r/m`, `EVEX.R`/`R'` set on the `71`/`72`/`73` shift groups, and `VCMPPS/PD` with `imm8 ≥ 32`
  (only bits 4:0 count); the decoder accepts them now, with oracle agreement.
* **Proof automation** (`TacticEVEX`) is not trusted: the zero-upper and compatibility
  theorems, `setZ_128`/`setZ_256` (an EVEX.128/256 write is WP-F's VEX write) and the simp lemmas
  are proved from the model.

## Floating point

Both models implement the scalar `float32`/`float64` instructions Go emits, bit-exactly, on a
shared IEEE 754 core (`Janus/Float/Core.lean`: exact values as dyadic rationals, rounding in the
five directions with tininess before and after rounding, round-to-odd quotients and square
roots, integer rounding; `Nat`/`Int` only, kernel-reducible on literals with `decide +kernel`).
What differs between the architectures is in the per-ISA wrappers, which transcribe the vendor
pseudocode:

| | arm64 (`Janus/Arm64/Float.lean`, ASL) | amd64 (`Janus/Amd64/Float.lean`, Intel SDM) |
|---|---|---|
| instructions | `FADD FSUB FMUL FNMUL FDIV FSQRT FNEG FABS FMIN FMAX FMINNM FMAXNM FMADD FMSUB FNMADD FNMSUB FCMP FCMPE FCCMP FCCMPE FCSEL FCVT` (S↔D) `FCVT{N,P,M,Z,A}{S,U} SCVTF UCVTF` (32/64-bit) `FRINT{N,P,M,Z,A,X,I}`, `FMOV` (register, immediate) | `ADD SUB MUL DIV SQRT MIN MAX` `SD`/`SS`, `UCOMISD COMISD UCOMISS COMISS`, `CMPSD`/`CMPSS` (predicates 0–7), `CVTSI2SD/SS`, `CVTTSD2SI CVTSD2SI CVTTSS2SI CVTSS2SI` (32/64-bit), `CVTSD2SS CVTSS2SD`, `ROUNDSD`/`ROUNDSS` (SSE4.1, which Go runs behind a `runtime.x86HasSSE41` test), `ANDPD ANDNPD ORPD ANDPS ANDNPS ORPS`, scalar FMA3 `VF{,N}M{ADD,SUB}{132,213,231}{SD,SS}` |
| control state | `State.fpcr`: `RMode`, `FZ`, `DN`, and FEAT_AFP's `FIZ`, `AH`, `NEP` | `State.mxcsr`: `RC`, `FTZ`, `DAZ`, the six masks |
| flags | `State.fpsr` (`IOC DZC OFC UFC IXC IDC`, cumulative) | `MXCSR` bits 5:0 (`IE DE ZE OE UE PE`, cumulative) |
| NaN results | the first signalling, else the first quiet operand (for `FMADD`: addend first), quieted; default NaN `0x7FF8…` with `DN = 1`; `AH = 1` has its own rules (default NaN negative, `FMAX` returns the second operand, ...) | the first source operand if it is a NaN, else the second, quieted; invalid operations give the indefinite `0xFFF8…`; `MINSD`/`MAXSD` return the second operand unchanged; FMA: the one NaN operand quieted, never negated (two or more NaNs fault) |
| tininess | before rounding (`AH = 0`), after rounding (`AH = 1`) | after rounding |
| flush-to-zero | `FZ`: inputs and outputs (output before rounding, `UFC` only, when `AH = 0`); `FIZ`: inputs | `DAZ`: inputs (no `DE`); `FTZ`: tiny results, exact or not, with `UE PE` |
| out-of-range to integer | saturates; NaN gives 0 (`IOC`) | the integer indefinite `2^(w-1)` (`IE`) |
| exceptions | a raised exception whose `FPCR` trap enable is set faults (`fpTrapped`); qemu and most cores have no trapping (the enable bits are RAZ) | an unmasked exception faults (`simdFPException`, `#XM`); an unmasked underflow traps on every tiny result |

**Feature assumptions.** The arm64 model is of a CPU with FEAT_FP and FEAT_AFP. With
`FPCR.{FIZ, AH, NEP} = 0` the AFP model coincides with Armv8.0's; on a CPU without FEAT_AFP those
bits are RES0, so a theorem whose precondition allows them set says nothing about such a CPU
unless they read as zero there. Half precision (FEAT_FP16: `ftype = 11`, `FZ16`, `AHP`), BFloat16,
`FRINT32*/64*`, `FJCVTZS`, fixed-point conversions and Advanced SIMD floating point are rejected.
The amd64 model is of SSE2 (and SSE4.1 for `ROUNDSD`, executed by Go only after testing
`x86HasSSE41`), of the packed SSE/SSE2/SSE3/SSE4.1 floating point of WP-D (each element by the
scalar operation, the flags of all elements ORed, `#XM` without a write if any element traps;
`RCPPS`/`RSQRTPS`, whose results are implementation-specific approximations, and `DPPS`/`DPPD`
are rejected) and of the scalar FMA3 instructions (`VF{,N}M{ADD,SUB}{132,213,231}{SD,SS}`,
which `GOAMD64=v3` code uses unconditionally and `GOAMD64=v1` code behind `x86HasFMA`): one
rounding of the exact `±a × b ± c` on the IEEE core, proved equal to IEEE 754
`fusedMultiplyAdd` in IEEE mode (`FP.fma_ieee`). WP-F adds the VEX forms of all of it at 128 and 256 bits (element-wise
over `l / w` elements, the same flag ORing and `#XM` rule), the 32 `VCMP` predicates, packed FMA3
(`FP.fma` per element) and F16C's `VCVTPH2PS` (exact; `DAZ`, `FTZ` and `DE` not applied) and
`VCVTPS2PH` (rounding from `imm8` or `MXCSR.RC`; `DAZ` applied, `FTZ` not). Where the manuals leave an FMA result open (two
or more NaN operands, whose choice Intel documents and AMD does not; `0 × ∞ + qNaN`, whose `IE`
IEEE 754 §7.2 leaves to the implementation) the instruction faults (`undefinedResult`), so no
proof depends on a vendor. The other VEX/EVEX floating-point forms and `LDMXCSR` are
rejected.

**x87** (C `long double`, `Janus/Amd64/X87.lean`; WP-J). The 80-bit double-extended format is
read through `X87.std` as the IEEE format (15, 63) of the same core; the precision control rounds
to 24, 53 or 64 bits with the extended exponent range, tininess is after rounding, NaNs follow
the x87 rules (SDM Table 4-7), unnormals, pseudo-infinities and pseudo-NaNs are invalid
operands, pseudo-denormals are read as their value. Each of these choices was checked on the
host (`docs/ORACLE-AMD64.md`, x87 mode). The model is *conservative* where the x87 is
asynchronous: an exception that is unmasked in the control word (or pending with `ES` set)
faults at the instruction that raises it, while the hardware completes it, stores a result
(for overflow and underflow a re-biased one) and raises `#MF` only at the next waiting x87
instruction; a stack overflow or underflow faults instead of delivering the masked response;
the reserved precision control `01` and `FNSTSW` of an undefined condition code fault. So every
run the model completes is a run of the hardware. `X87.binop_add_ieee`/`binop_mul_ieee` (proved)
connect `FADD`/`FMUL` at 64-bit precision to `Janus.Float.Spec.add`/`mul` on (15, 63); the
`long double` examples state their results with them. The instruction/data pointers and the
last opcode (`FNSTENV`/`FSAVE` state) are not modelled, and the instructions that would expose
them are rejected. Encodings whose behaviour the manuals leave open (an `FCMP #0.0` with a non-zero `Rm`
field, `REX.W` on an SSE instruction that does not use it, reserved `CMPSD`/`ROUNDSD` immediate
bits) are rejected rather than guessed.

**State and quantification.** `FPCR`, `FPSR` and `MXCSR` are state fields, arbitrary in every
call state unless a precondition fixes them; no accepted instruction writes the control bits
(`MSR FPCR`, `LDMXCSR` are not decoded), so a run keeps the caller's values. Linux starts every
process with `FPCR = 0` and `MXCSR = 0x1F80`, and Go never changes the *control* bits (Go's
`abi-internal.md` fixes them at every call). The *status* flags are another matter: they are
sticky, and Go's own floating point raises them. `MXCSR` holds both, and in a running Go program
it is already `0x1FA0` (`PE` set) when `main` starts (`audit/rt-fp/probe/mxcsr`). So the amd64
examples state `GoABI.GoMXCSR s` (the control bits of `0x1F80`, reserved bits zero, **any**
flags), not `s.mxcsr = 0x1F80`, which no call from initialised Go code satisfies
(`docs/AUDIT-FP.md`, X64-MXCSR-STICKY). On arm64 the flags live in `FPSR`, which the examples
leave arbitrary; they state `s.fpcr = 0` (what a Go program sees) and, on arm64, an `exact`
theorem for every `FPCR` without trap enables. On return, Go's ABI treats `FPSR` as scratch and
calls the `MXCSR` status bits callee-save, but Go code does not preserve them (an inexact
`ADDSD` sets `PE`, and nothing restores it; `AddF64` is an example). `ABIReturn` therefore does
not include them, and "obeys the ABI" in a theorem says nothing about `FPSR` or the `MXCSR`
flags, except where a theorem states them explicitly.

**Specifications.** `Janus/Float/Spec.lean` states the IEEE operations independently of the
architectures: `add`, `mul`, `fma` (`none` when the IEEE result is a NaN), `abs`, `truncInt`, and
`ResultIs f spec x` (the delivered encoding `x` is exactly the IEEE result, or some NaN when that
is a NaN; IEEE 754 does not fix the NaN, so neither does the specification). The bridge lemmas
`Janus.Arm64.FP.fpAdd_ieee`/`fpMul_ieee`/`fpMulAdd_ieee`/`fpToFixed_rzu_ieee` and
`Janus.Amd64.FP.binop_add_ieee`/`binop_mul_ieee` prove that the models compute these in IEEE
mode (no flushing, no default NaN, no alternate handling; any rounding direction); they are
proved, not trusted.

**Validation.** The core and both wrappers are checked against qemu and the Arm ASL (Sail) on
arm64, the host CPU on amd64, and Berkeley TestFloat/SoftFloat (`scripts/testfloat.sh`); see
`docs/ORACLE.md`, `docs/ORACLE-SAIL.md` and `docs/ORACLE-AMD64.md`.

## Runtime contracts

A theorem can rely on a runtime function it does not execute by stating the function's
behaviour as a hypothesis (docs/RUNTIME-CONTRACTS.md). The mechanism adds nothing to the trusted
base:

* `janus extract --contract SYM` leaves the function out and records it in
  `Extracted.program.contracts`. The list is part of the byte-compared extraction (`janus check`
  regenerates it from the recorded patterns) and does not change the run: there is no code at a
  contract address, so reaching it is `noCode`. Leaving out a function can only make a theorem
  unprovable, never a false one provable.
* The theorem is stated about `Extracted.program.link impl` for **every** `impl : List Segment`
  satisfying the contract hypotheses, which are ordinary `Summary` propositions printed as part
  of the statement and audited like the rest of it. The real binary is one such `impl` (its
  runtime code at those addresses, run by the same model), so the theorem holds of it exactly
  when the real runtime meets the contracts. A contract on `Extracted.program` itself would be
  false (no code there) and is never used.
* **A contract must be satisfiable, and by the real runtime** (round 9 C1). A `Summary` is a
  claim about every state that meets its precondition; before round 9 the allocation contracts'
  precondition said nothing about the runtime's own state, so they demanded a fresh writable
  object from states with no heap mapped and requests up to `maxAlloc` (2^48 bytes). No code
  meets that (`audit/round9/model/Unsat.lean` proves it false for every program, address and
  `rt`), so every theorem assuming one was vacuous. Every allocation contract now takes a
  readiness predicate `H : RtReady`, required at the call for the call's arguments, `g`, `SP`
  and the runtime's view of memory (`rtView rt`: the bytes inside `rt` and the regions); the
  theorem quantifies over `H` and assumes it at its entry. The real runtime meets the contract
  with `H` = "the runtime's code returns as described from every call state with these
  arguments, `g`, `SP` and runtime memory", and `audit/round9/controls/NewPair_witness.lean`
  kernel-checks an implementation, `rt`, `H` and a call state for which NewPair's theorem fires.
  A new contract needs such a witness too.
* **The theorem must quantify the runtime** (round 10 V1). A satisfiable contract becomes an
  unsatisfiable hypothesis when the statement picks its runtime arguments: with
  `H := fun _ _ _ _ => True` the allocation contract is round 9's false one again, and a proof
  "verified" that NewPair returns 42. The auditor rejects a statement that applies a runtime
  contract (a `Janus.Contracts` definition whose body is a `Summary`), anywhere but as its whole
  conclusion, to anything but variables of the statement for its runtime parameters (`impl` in `Extracted.program.link
  impl`, the ranges `rt`, the readiness predicate `H`, the models `R`, `M`), or in which a premise
  other than a contract or the model laws (`R.Laws`, `M.Laws`) mentions one of those variables,
  and a dependency definition that applies a contract. Not checked: constraints the theorem's
  own precondition puts on them, and the numeric parameters (`stack`); read those like any
  precondition. Also admitted (integration of wave 1): premises that bound a model's stack
  depth (`8 ≤ R.depth`, `R.depth + 48 ≤ d` with `d` a non-runtime variable of the statement),
  which cannot pin a runtime argument; a conclusion that is a conjunction of contracts (a theorem
  proving several, `gcWriteBarrier1..8`) claims each. A contract stated over runs instead of as a
  `Summary` (`GopanicRecoverContract`) is recognised by its name `…Contract` and its `Program`
  parameter.
* **Every runtime argument is a free variable, whatever its type** (round 11, red-team 11a L1a/H1a/P1a/K1a).
  Round 10 V1 recognised the runtime parameters by a list of types (`RtReady`, `IfaceModel`,
  `MapModel`, `List (Nat × Nat)`), so a contract over any later model type (`MemModel`, `HashModel`,
  `PanicRuntime`, `CheckptrModel`, `CgoCheckModel`, and on the live-contract branches `RtInv`,
  `PoolShape`) escaped the rule: a proof could pin `R := closed {inv := True, rt := [] …}` or
  state `hP : M = M0` / `hCb : ∀ m g q, C.base m g q = 0`, the contract became unsatisfiable (or
  the straddle precondition vanished), and `janus verify` printed Verified for a false claim. The
  rule is now default-deny (`contractParamKind` in `Janus/Tools/Audit.lean`): in a runtime contract
  the program must be `Extracted.program.link impl`, a scalar (`Nat`, `Int`, `Bool`, `Fin`,
  `BitVec`, `UIntN`: an entry address, stack bound, count) may be anything, and EVERY other
  argument is a runtime parameter that must be a variable bound by the statement, not a `let`, not
  instantiated, and mentioned by no premise except runtime contracts, `….Laws M` of a framework
  model, and the stack-depth bounds above. A new model type is therefore covered with no change to
  the auditor. Regression rows: `audit/round11/` (closed `HashModel`, `HashModel` pinned by
  `H = H0`, closed `PanicRuntime`, `CheckptrModel` pinned by a premise, with the honest theorems
  as controls and the unsatisfiability of the closed models kernel-checked).
* **Readiness is per call** (round 10 V2, V3). A contract whose postcondition hands back all its
  precondition needs can be chained without bound from one state. For the map contracts that
  allocate and keep (`Assign`, `MakeSmall`), this contradicted `MapModel.Laws` outright
  (`audit/round10/model/MapUnsat.lean`), so every theorem using them was vacuous; for the
  interface contracts that allocate (`convT*`, `typeAssert`, `interfaceSwitch`) it was
  unsatisfiable by the real runtime in the model (fixed regions, no collector). They now take a
  readiness predicate `H` like the allocation contracts, required at the call and not handed back.
* `p.link impl` fetches `p`'s word wherever `p` has code (`Program.fetch_link`), so the proof
  learns nothing about `impl` except through the hypotheses.

**What a contract hypothesis assumes about the runtime** (in the model, which is single-threaded:
no concurrent GC, no preemption):

* **Allocation** (`Janus/Contracts/Alloc.lean`, `AllocAmd64.lean`). `mallocgc`, `newobject`,
  `makeslice` and `growslice` return a fresh, aligned, writable object (zeroed as Go specifies)
  inside the caller-declared runtime-owned ranges `rt`, change memory only inside `rt` and their
  stack window, and preserve the ABI's callee-saved registers, **when the runtime is ready for
  the call** (`H`, above). Caveats that are assumptions of every such theorem: (1) *runtime-owned
  memory* is a visible parameter `rt`; the caller's data must be outside it (stated in the
  precondition); (2) the object's memory is a region already in the state (instructions cannot
  add regions; Go reserves arenas up front); a call that needs `mmap` is one `H` excludes;
  (3) one allocation per theorem: the contracts do not record that an allocated object leaves
  `rt`, and `H` is stated for the call made from the entry state; (4) the runtime uses at most
  `stack` bytes below `SP` (4096 in the examples) and **the goroutine stack does not move**: Go
  may grow and copy the stack inside a slow path (`morestack`), and a GC assist that scans the
  goroutine's own stack may shrink it (`scanstack` → `shrinkstack`), relocating the caller's
  frame and changing `SP`; such calls are not ones the contract describes, so `H` excludes them;
  (5) the GC's concurrent work (marking, sweeping, assists, finalizers) and other threads are
  outside the model: `H` is a property of the call state in the single-threaded model, and
  whether another thread changes the runtime's memory during the call is not covered; Go's
  collector does not move objects, so a returned pointer stays valid; (6) a pointerful object
  of more than 512 bytes (up to `maxSmallSize - 8`) follows an 8-byte malloc header and is only
  8-aligned (`mallocHdr`, round 9 C2; Go 1.26 returns `slot + 8`).
* **String comparison** (`Janus/Contracts/Cmpstring.lean`, `CmpstringAmd64.lean`).
  `runtime.cmpstring` returns the bytewise lexicographic comparison (`strCmp`, `-1`/`0`/`1`) of two
  readable strings, changes memory only in its stack window and preserves the ABI's callee-saved
  registers. The contract is shown satisfiable by a verified byte-loop implementation on both ISAs
  (`CmpstringSat.cmpstring_satisfiable`, `CmpstringSatAmd64.cmpstring64_satisfiable`); that Go's `cmpbody` meets it is assumed.
* **Interfaces** (`Janus/Spec/Type.lean`, `Janus/Contracts/Iface.lean`, `IfaceAmd64.lean`;
  docs/RUNTIME-CONTRACTS.md, "Interfaces"). `convT`, `convTnoptr`, `convT16/32/64`,
  `convTstring`, `convTslice`, `assertE2I`, `assertE2I2`, `typeAssert`, `interfaceSwitch`,
  `efaceeq` and `ifaceeq` as `Summary`s over an abstract model `R : IfaceModel` that the theorem
  quantifies over (and, for the allocating ones, a readiness predicate `H`; round 10 V3).
  `typeAssert` requires a non-nil type (round 10 I1: with a nil type the runtime faults in about
  one call in 1000, rebuilding its cache with `buildTypeAssertCache(oldC, nil, nil)`). Trusted, as claims about the Go 1.26 runtime: (1) each contract (a box in the
  runtime's memory holding the value; the itab `getitab` returns, or `0`; `switchCase`'s first
  implemented case; `efaceEqual`/`ifaceEqual`), with every panic and throw path excluded by its
  precondition; (2) the laws `R.Laws` (descriptors readable in `R.priv`, itabs non-zero, a
  `TFlagRegularMemory` type compares its `Size_` bytes); (3) where a theorem uses it,
  `StaticItabs` (`getitab` returns the static `go:itab.*` objects: `runtime.itablink` lists every
  reachable itab and `itabsinit` adds them before Go code runs, so no plugins or shared
  libraries); (4) the cache invariants `TACacheOK`/`ISCacheOK` as what the runtime maintains
  (`buildTypeAssertCache`, `buildInterfaceSwitchCache`; the empty caches satisfy them); (5) our
  reading of the `internal/abi` layouts. The code is the runtime's: the extractor pins these
  thirteen functions like stubs (`runtimeContractStubs`, below), their callees by name only. Every
  contract is satisfiable (`Janus/Contracts/IfaceSat.lean`, `IfaceSatAmd64.lean`: a model, code
  and a state satisfying the precondition), so no theorem using them is vacuous by an
  unsatisfiable contract; each interface example also proves its whole hypothesis set jointly
  satisfiable for its binary and its conclusion reached (`Proof.Witness.nonvacuous`, `.returns`). Boxes are not known to keep their value across later runtime calls.
* **Equality, hashing and typed memory** (`Janus/Contracts/Mem.lean`, `Hash.lean`, `MapStr.lean`
  and their amd64 files; docs/RUNTIME-CONTRACTS.md, "Equality, hashing and typed memory"). The
  contracts of `memequal`, `memequal0/8/16/32/64/128`, `memequal_varlen`, `f32equal`, `f64equal`,
  `c64equal`, `c128equal`, `strequal`, `interequal`, `nilinterequal`, `memhash`, `memhash0/8/16/32/
  64/128`, `memhash_varlen`, `strhash`, `f32hash`, `f64hash`, `c64hash`, `c128hash`, `interhash`,
  `nilinterhash`, `typehash`, `rand`, `typedmemmove`, `typedmemclr`, `memclrHasPointers`, their
  callees `memmove`, `memclrNoHeapPointers`, `bulkBarrierPreWrite`, and `mapaccess2_faststr`.
  Trusted, as claims about the Go 1.26 runtime: (1) **the hash is a model**: a theorem quantifies
  over every `H : HashModel`, whose byte hashes `mem`/`mem32`/`mem64` are uninterpreted functions
  of the seed and the bytes; the contracts claim the runtime's `memhash` & co. compute *some*
  such function for the process (true for both the AES and the `wyhash` paths: they depend only
  on the seed, the bytes and the per-process key, which `H.Env` keeps fixed), that `f32hash`/
  `f64hash` map `±0` to `c1·(c0 ^ h)` and a NaN to `c1·(c0 ^ h ^ rand())`, and that `typehash` of
  a `TFlagRegularMemory` type is the byte hash (`HashModel.Laws.regular`); everything a map needs
  of the hash is then proved (`Janus/Contracts/HashLaws.lean`: `feq_eq`, equal floats have equal
  encodings unless both are zeros; `fhashIs_of_feq`, `fhashIs_nan`, `strhash_of_strEq`);
  (2) **the write barrier is off** for the typed-memory contracts (`WriteBarrierOff`, the flag word
  at `wb` is 0; with it on the barrier's buffer changes too, which these contracts do not state);
  (3) the inputs are readable in the model's byte-exact memory: the amd64 `memeqbody` reads up to
  7 bytes around a short input (within its page), so on amd64 `memequal` and `memequal_varlen` stay assumptions,
  while on arm64 its machine code is proved to meet the contract; (4) a `map[string]V` is keyed by
  the strings' contents (`MapStr.Access2Str`), which the hash and equality laws justify. The code
  is the runtime's: the extractor pins every one of these functions except `typehash`, whose jump
  table makes its normalized code program-dependent (`runtimeContractStubs`, `runtimeFuncDir` for
  the ones `internal/bytealg` and `internal/runtime/maps` define). Every contract is satisfiable
  (`Janus/Contracts/MemSat.lean`, `HashSat.lean`, `MapStrSat.lean` and the amd64 files: models
  `M0`, `H0`, `R0`, `MS0`, code and a state), and every example proves its hypotheses jointly
  satisfiable and its conclusion reached (`Proof.Witness.nonvacuous`, `.returns`). **Proved from
  the machine code rather than assumed** (`examples/proofs/Alg*.lean`, `Mbar*.lean`,
  `examples/proofs-amd64/Alg*/`, `Mbar*/`): the runtime's own equality, hash and typed-memory
  functions meet their contracts given the contracts of their callees.
* **Maps** (`Janus/Spec/Map.lean`, `Janus/Contracts/Map.lean`, `MapVar.lean`, `MapStr.lean` and
  their amd64 files; docs/RUNTIME-CONTRACTS.md, "Maps"). The contracts of `makemap_small`,
  `makemap`, `mapaccess1`, `mapaccess2`, `mapassign`, `mapdelete`, `mapaccess1_fat`,
  `mapaccess2_fat`, the `_fast32`, `_fast64`, `_fast64ptr` and `_faststr` entry points,
  `mapclear`, `mapIterStart` and `mapIterNext`, as `Summary`s over an abstract model
  `M : MapModel K V` that the theorem quantifies over (`Rep`, `Iter`, `Typ`, `Env`, `priv`,
  `depth`). Trusted, as claims about the Go 1.26 runtime: (1) each contract's effect on the
  abstract map (`AMap`), the same model for every entry point of a map type; (2) the laws
  `M.Laws` (the representation lives in `M.priv`, the header's first word is `len`, finitely
  many keys); (3) **readiness of the allocating calls** (`makemap*`, `mapassign*`): they take
  `H : RtReady` like the allocation contracts (finding R3-C1: without it the old `Assign` and
  `MakeSmall` were false for every implementation, `audit/maps/model/Unsat.lean`, so `Insert`,
  `InsertGet` and `NewMap` were vacuous), one allocating map call per theorem; the read-only
  entry points keep the perpetual `M.Env`; (4) the key semantics of each entry point: 8- and
  4-byte words, string content (`strKey`; a key stored by `mapassign_faststr` must lie in the
  runtime's memory, `StrOwned`, since the map keeps pointing to it), and for the generic entry
  points `n` bytes of a `TFlagRegularMemory` key type (`KeyRegular`, read from the descriptor in
  the runtime's memory), which R4's hash and equality laws justify; key types with floats,
  strings or interfaces inside are not covered; (5) keys and iterator structs outside the
  callee's stack window (and on amd64 the iterator off the return-address slot); (6) no
  modification of a map during a `range` over it, no nil-map assignment (it panics), no
  stack-allocated `makemap` header, and the concurrent-access checks (`fatal`) unreachable in
  the single-threaded model. The code is the runtime's: the extractor pins all 24 map entry
  points like stubs (`runtimeContractStubs`; `runtimeFuncDir` for the ones `internal/runtime/maps`
  defines). Every contract is satisfiable (`Janus/Contracts/MapSat.lean`, `MapVarSat.lean`,
  `MapStrSat.lean`, the amd64 files; models `ME`, `MC` of `MapModel0.lean`, code and a state with
  a non-nil map), and every R3 example (and `SumValues`) proves its hypotheses jointly
  satisfiable (`Proof.Witness.nonvacuous`). **Proved from the machine code rather than assumed:**
  `mapaccess1_fast64` on small maps (`MapAccess1Small`, both ISAs).
* **Strings and slices** (`Janus/Contracts/Rt.lean`, `String.lean`, `Slice.lean`;
  docs/RUNTIME-CONTRACTS.md, "Strings, slices and the write barrier"). The string conversions and
  concatenations, the UTF-8 helpers, `growslice` for any element type, `makeslicecopy`,
  `moveSlice*`, `slicecopy`, `typedslicecopy`, `wbZero` and `wbMove` as `RtSpec`s turned into
  `Summary`s (`RtContract`, `RtContract64`). Trusted, as claims about the Go 1.26 runtime: each
  spec, with its panic and throw paths excluded by its precondition and, through `H`, the calls
  the runtime does not serve as described. Not trusted: the UTF-8 decoder `decodeRune` is checked
  against the runtime's own output (`JanusTests/String.lean`), and `decoderune` and `countrunes`
  are proved from their machine code on both ISAs (`examples/proofs/SumRunes.lean`,
  `RuneLen.lean` and their amd64 counterparts). Every spec has a satisfiability witness
  (`Janus/Contracts/Sat.lean`, `SatAmd64.lean`, collected in `RtSat`); `audit/rtstr/run.sh`
  checks the capacity formulas and the examples against the real runtime.
* **Panics, defer, recover** (`Janus/Spec/Panic.lean`, `Janus/Contracts/Panic.lean`,
  `PanicAmd64.lean`; docs/RUNTIME-CONTRACTS.md, "Panics, defer, recover"). `gopanic`,
  `gorecover`, `deferproc`, `deferprocStack`, `deferreturn`, `deferprocat`, `deferrangefunc` as
  `Summary`s (and, for `gopanic`, a continuation) over an abstract model `P : PanicRuntime` that
  the theorem quantifies over. Trusted, as claims about the Go 1.26 runtime: (1) each contract,
  in particular that `gorecover` returns the panic value exactly when its caller is not a wrapper
  and the caller's saved return address (`[FP + 8]`) is the running deferred call's return point
  (our reading of `gorecover`'s `p.argp`/frame check), and that `gopanic` runs the frame's one
  pending open-coded defer (funcval from the stated slot, `deferBits` at the stated offset) and,
  if it recovers, resumes the frame at the stated `deferreturn` site with `SP` and the frame
  pointer restored; (2) the laws `P.Laws`; (3) the **funcdata offsets** in the `gopanic`
  contract (`FUNCDATA_OpenCodedDeferInfo`, `_func.deferreturn`) are parameters printed in the
  statement, not read from the binary: a wrong offset makes the hypothesis false of the real
  runtime, so the theorem is then vacuous for it (the satisfiability theorem and
  `Proof.Witness` only show it consistent); (4) the **fault classification** in `goClass`: a
  memory fault at an address below `0x1000` is Go's nil-dereference panic (`P.err .mem`), which
  assumes page 0 (`[0, 0x1000)`) is unmapped, the kernel delivers `SIGSEGV` with `si_addr` the
  faulting address, and `runtime.sigpanic` takes the `panicmem` path (`sigcode1 < 0x1000`); on
  amd64 a `#DE` is `panicdivide`. The classification only names which panic value a stop
  is; it never turns a stop into a return. (5) The `runtime.panic*` stubs panic with
  `P.err k` for the kind `panicStubErr` assigns (`boundsError`, `divideError`, ...). The code is
  the runtime's: the extractor pins these eight functions (`runtimePanicContractStubs`, with
  `sigpanic`) like the interface contracts. Every contract is satisfiable
  (`Janus/Contracts/PanicSat.lean`, `PanicSatAmd64.lean`), and the examples with contracts
  (`DeferTwice`, `RecoverSet`) prove their whole hypothesis set jointly satisfiable for their
  binary and their conclusion reached (`Proof.Witness.nonvacuous`, `.returns`). Out of scope:
  nested panics, `Goexit`, several pending defers in one `gopanic`.
* **Write barriers** need no contract: the barrier's fast path (`runtime.gcWriteBarrier2`,
  `gcWriteBarrier`, the buffer append) is extracted and executed. For proofs that leave the
  barrier out, `WbContract`/`WbContract64` (`Janus/Contracts/WriteBarrier.lean`) are met by the
  real `gcWriteBarrier1..8` whenever the buffer has room (`examples/proofs/WriteBarrier.lean`,
  `examples/proofs-amd64/WriteBarrier`; `HRoom` held at every non-flushing real call probed). Only the buffer flush
  `runtime.wbBufFlush` is left out, and the examples' precondition (the P's `wbBuf` has room)
  makes it unreachable. The runtime fields the barrier uses must each be separate from the
  stored-to field and the stack (round 9 S1: one interval holding them all, as before, failed
  for about half of the real calls with the barrier on). The precondition states the flag `runtime.writeBarrier.enabled` (as the
  word the code reads), and the barrier's field offsets are read off its code.
* **The allocator fast path is proved, not assumed** (arm64, `examples/proofs/MallocFast.lean`):
  for a pointer-free request of 16 to 1016 bytes, `runtime.mallocgc` and the inlined
  `nextFreeFast`/`getMCache`/`acquirem`/`releasem` paths of `runtime.mallocgcSmallNoscan` are
  executed from the binary's machine code under `MCacheOK` (a well-formed `g`/`m`/`p`/`mcache`/
  `mspan` state for the request's size class with a free slot in the span's `allocCache`, the
  slot zero and `span.needzero = 0`, the runtime globals readable, every object separate; each
  global on its own, since one range spanning them covers `runtime.m0` in `.bss`, which made the
  statement false for every call on the main thread's `m`, round 9 M1).
  Everything else of `mallocgc` stays trusted, and is not even assumed by that theorem, because
  `MCacheOK` makes it unreachable: the tiny allocator (`mallocgcTiny`), pointerful objects
  (`mallocgcSmallScan*`), large objects (`mallocgcLarge`, `mheap`, `mmap`), span refill
  (`(*mcache).nextFree` → `mcentral`/`mheap`), clearing a dirty slot (`memclrNoHeapPointers`
  when `span.needzero`), GC assist (`deductAssistCredit`, `gcBlackenEnabled ≠ 0`), allocate-black
  during GC (`gcmarknewobject`, write barrier on), heap profiling (`profilealloc`), the GC trigger
  (`gcTrigger.test`, `gcStart`) and the debug hooks (`debug.malloc`). Contracts that rely on
  these paths (the allocation contracts above, used by `NewPair` & co.) remain assumptions.
* **Remaining runtime (R9)** (docs/RUNTIME-CONTRACTS.md, "Remaining runtime"). Trusted, as claims
  about the Go 1.26 runtime:
  1. *Data objects.* `runtime.zeroVal` holds 1024 zero bytes, `runtime.inf` the word `+∞`,
     `runtime.cgoAlwaysFalse` the byte `0` whenever user code runs (`ZeroVal`, `RuntimeInf`,
     `CgoAlwaysFalse`, stated as hypotheses at the address the code reads, since the extractor
     does not copy writable data). `runtime.staticuint64s` is read-only and extracted: its
     contents are proved, not assumed.
  2. *CPU feature flags.* A theorem takes a flag's value as a parameter and holds for both values
     (`CpuFlag`). The model executes every instruction it decodes on any CPU; a `true` flag case
     is meaningful for the real machine exactly when `internal/cpu` sets the flag only on CPUs
     that implement the guarded instructions (which it does from `CPUID`/`HWCAP`).
  3. *Checks and the size-specialised allocator.* `CheckptrAlignment`, `CheckptrArithmetic`,
     `CgoCheckPointer`, `CgoCheckResult` (and the amd64 forms) state that the runtime's check
     returns, changing only runtime-private memory and its stack window, when it passes; the
     conditions are the runtime's own (`AlignOK`, `ArithOK`) over the abstract `checkptrBase`, or,
     for cgo, the abstract predicates of `CgoCheckModel`. `MallocgcSmallNoScanSCContract` & co.
     are the `RtReady` `mallocgc` contract at the entry's fixed size class. All are pinned to the
     runtime's code and proved satisfiable.
  4. *Build modes.* `-cover`, `-d=checkptr`, `-spectre=ret` and `GOEXPERIMENT=sizespecializedmalloc`
     builds are accepted (the instrumentation is ordinary code, or calls pinned contracts);
     `-race`, `-msan`, `-asan`, `-d=libfuzzer` are rejected by the extractor, which detects them from
     the binary's symbols (the sanitizer runtimes' entry points), sections and `debug/buildinfo`
     settings. Their semantics depend on the sanitizer runtimes' shadow state, which the model does
     not have; a binary that hides those markers is outside what the detection covers.
  5. *Soft float.* Nothing about `-d=softfloat` is assumed: `f32to64` is proved; Go's `fadd64`
     does not implement IEEE 754 for subnormal results (RUNTIME-CONTRACTS.md), so no contract
     claims it does.
* **amd64**: every amd64 contract requires the return address at `[RSP]` below `2^47` (a
  canonical user address); without it no code could return and the contract would be
  unsatisfiable.

## Dynamic calls, closures and `defer`

An indirect call (`BLR`/`BR`; amd64 `CALL`/`JMP` through a register or memory) jumps to the value
the register holds, in the model as on hardware. Nothing about Go's type system is assumed:

* **Which code a dynamic call reaches is a hypothesis of the theorem when it is not computed
  by the code being proved.** `Janus.Spec.ItabIs ds m tab name` (the interface's itab word is the
  address of the static itab `name` of the extracted data, and memory holds its bytes
  read-only), `FuncvalIs m fv fn` (a funcval's code word) and `ClosureCtx m fv vars` (the captured
  variables after it) are ordinary propositions about the call state's memory and appear in the
  printed statement; the auditor treats them like any other part of the statement. A theorem
  says nothing about calls whose interface or func value is not the one stated. If the stated
  itab or funcval cannot be in memory as described, the theorem is vacuous for those callers,
  like any unsatisfiable precondition.
* **Itab contents come from the binary.** `ItabIs` names a data object of
  `Extracted.program.data`, copied byte for byte from `.rodata` (a static itab `go:itab.*T,I`)
  and re-checked by `janus check`. Dynamically built itabs (`runtime.getitab`, for type
  assertions to interfaces the compiler did not see) are heap objects, not covered by
  `ItabIs`; state their memory directly if needed.
* **Object names must resolve** (round 8 I1). `ItabIs`, `dataNamed`, `dataAddr`, `dataLen`,
  `dataWord`, `itabFun`, `segWord`, `segAddr` (arm64 and amd64), amd64 `dataBase` and
  `Program.contractAddr` (both ISAs; round 9 I1g: a name that is not a recorded contract gives
  address 0) look an
  object up by name (or index) and fall back to `False` or `0` when there is none, so a misspelt,
  absent or lookalike name (`MulHаsher` with a Cyrillic `а`) makes a statement vacuous or about
  address 0 while it reads as a claim about that object. The auditor therefore requires, in the
  statement (after proof-local definitions are expanded) and in every dependency definition it
  uses, that each such name is a string literal (an index: a numeral) naming an object of
  `Extracted.program` (an `ItabIs` name must be a static itab, `go:itab.…`), and that the
  program or data argument is `Extracted.program` (`.data`).
* **Bound variables must be told apart** (round 7 H1, round 9 H2). Two binders of a statement
  or of a proof-local definition that read the same once lookalike letters are folded to Latin
  are rejected, and a binder may only use ASCII letters, digits, `_ ' ! ?`, subscripts, basic
  Greek, the mathematical script/fraktur/double-struck letters and the letterlike symbols the
  fold maps. Polytonic Greek (`ό` U+1F79 is `ό` U+03CC), the accented/Coptic range and the other
  letterlike symbols (`K` KELVIN SIGN is `K`) are rejected outright.
* **Targets are untrusted extraction choices.** `janus extract --targets` and the extractor's
  inference (code addresses computed by user code, itabs and funcvals it loads) only decide
  which code is copied, like reachability. A target that is not copied makes the call fault
  (`noCode`), so no theorem through it can be proved; extra targets add code no theorem has to
  mention. What was added and why is recorded in `identity.json` (`targets`,
  `dynamicTargets`).
* **Open-coded defers are modelled as the code that implements them**: the deferred closure is
  an ordinary stack-allocated funcval called at each exit. `runtime.deferreturn`, which an
  open-coded function calls only from the block the runtime resumes at after a *recovered*
  panic, is not extracted unless named with `--contract` (`omittedCalls` in `identity.json`): if
  a run reached it, it would fault, so a theorem that returns shows it is not reached. With
  `--contract runtime.deferreturn` it is the `DeferreturnContract` hypothesis (above).
* **Panics, `recover` and heap defers go through the panic contracts** (above). Without
  `--contract runtime.gopanic` a panic is a stub outcome: the run ends at
  `runtime.gopanic`/`runtime.panic*` (`EnsuresGo` reports it as `.panicked v`), and the deferred
  calls the runtime would run while unwinding are not executed, so such a theorem says nothing
  about them. Defers the compiler does not open-code (in loops, or more than 8 in a function)
  allocate defer records with `runtime.deferproc*` and call `runtime.deferreturn` at every exit;
  without `--contract` on them the exit faults. Heap-allocated closures (`runtime.newobject`)
  are runtime calls like any other allocation.

## FFI (cgo)

A theorem about Go code that calls C (see [FFI.md](FFI.md)) is stated with `EnsuresC p C …`,
where `C` is a `Contract` for the external stubs, and it is written in the statement:

* Under `CgoSpec fn G E`, the theorem *assumes* a behaviour of the C call. It is a conditional
  statement, and the assumption is visible in the printed statement.
* Under `CgoCall p`, the theorem assumes only the trusted contract of the cgo boundary. Every
  instruction of the Go code, the cgo wrappers and the C code is executed by the model from the
  binary's bytes. The C code runs inside the contract, on `p`.

**What `CgoCall` trusts** (listed in full in [RUNTIME-CONTRACTS.md](RUNTIME-CONTRACTS.md),
"FFI (cgo)"):

* the stack switch: `asmcgocall` makes a C call of the wrapper on a system stack of at least 4096
  free bytes that is not Go memory, with the Go memory otherwise unchanged;
* the scheduler: `entersyscall`/`exitsyscall` change only the goroutine stack below `SP`,
  `cgocall`'s spill slots, the `g` struct and the TLS `g` slot, and the goroutine may resume on
  another thread;
* the return: `cgocall` returns to its caller with `SP`, `g` and `FP` restored (amd64: also
  `X15 = 0`, `DF` clear and the TLS `g` slot);
* `_cgo_topofstack` returns one value throughout a cgo call and preserves everything else.
* the floating-point environment at the C entry: the C code starts with the Go caller's `FPCR`
  (arm64, `CgoEntry.fpcr`) and with its `MXCSR` control bits and x87 control word (amd64,
  `CgoEntry.mxcsr`, `CgoEntry.fpucw`): `asmcgocall` switches only the stack and `g` and executes
  no `MSR FPCR`, `LDMXCSR` or `FLDCW` (`runtime/asm_arm64.s`, `runtime/asm_amd64.s`).

The granted memory must contain no runtime-internal memory (`m`, `p`, the scheduler, the `g0`
stack). For an execution whose granted regions overlap those, the theorem says nothing.

**Consequences.**

* *`X18` on arm64.* `EnsuresC` uses `ABIReturnC` (`SP`, `g`, `FP`) instead of `ABIReturn`: C code
  may use `X18` (a temporary in AAPCS64 on Linux) and `cgocall` does not restore it. Go code never
  reads it.
* *Callbacks.* C calling back into Go goes through the trusted `CgoCallback` contract (below);
  `crosscall2` (Go assembly), the cgo-generated C wrapper and the exported Go function are
  extracted and executed.
* *Safe by construction.* A contract stub is only passed with its `safe` predicate proved, and a
  `ReturnsC` proof covers *every* result its `next` relation allows. `CgoCall` requires the C run
  to terminate with the callee-saved registers restored for every admissible C call state.
* *Why not a `Summary` hypothesis.* A `Summary` about the extracted program at `cgocall`'s
  address (where no code is copied) is false, so a theorem assuming one would be vacuous. The
  contract semantics avoids this: the only way to discharge `CgoSpec` is the refinement theorem
  `CgoCall.refines`.

### The C environment (K2: `Janus.FFI`, `Janus.Contracts.Libc`, `cmd/janus/cenv.go`)

What a C-environment theorem trusts, beyond the model:

* **The extractor's ELF reading**, where a wrong answer is not caught by a proof:
  * *PLT naming.* A stub `sym@plt` is created only for a canonical PLT sequence whose GOT slot is
    the target of a `JUMP_SLOT` relocation naming `sym`; the theorem then assumes the dynamic
    linker binds `sym` to the libc function the contract describes (symbol interposition,
    `LD_PRELOAD` and a different libc are outside the statement).
  * *Static GOT slots.* A slot in `PT_GNU_RELRO` with no dynamic relocation is copied as constant
    read-only data. This trusts that no relocation (static or dynamic) the extractor does not
    read changes it; `-z norelro` binaries have no such slots and their GOT loads fault.
  * *TLS layout.* `Extracted.tls` and `TLSImage.a64Addr`/`x64Addr` encode the ELF TLS ABI
    (variant I on arm64, variant II on amd64) for the executable's block; `TLSBlock` (a
    precondition) states the block is in place, and on amd64 that the TCB's first word is its own
    address. Blocks of `dlopen`ed modules are only reachable through `__tls_get_addr`/TLS
    descriptors, whose contracts (`TlsGetAddr`, `TlsDescFn`) are hypotheses or trusted.
  * *`checkCgoTLS`* (a finding of this package): the `cgocall` contracts put Go's TLS `g` slot at
    `FS − 8` / `TPIDR_EL0 + 16`, which is wrong in a binary whose C code has `__thread`
    variables (the linker moves `runtime.tlsg`). Such extractions are refused; the stub pins also
    mask the TLS displacement so the pinned code is recognised in either layout.
* **The libc contracts** (`Libc`, `SetJmp J`, `TlsGetAddr`): glibc on Linux, each function's
  effect as stated in FFI.md § 3.2–3.4, with libc's stack use bounded by `libcStack = 32768`
  bytes below `SP`. `malloc` returns fresh memory disjoint from every region of the state (the
  model's address space is what the precondition granted, so a block may not overlap Go memory
  or the stack). The heap **ghost tokens** (`heapToken`, at `2^48 + p`) are a proof device: no
  instruction can access them (accesses need `< 2^48`), they only record which blocks `free` may
  release. `setjmp`/`longjmp` are stated over every `jmp_buf` model with the `JmpModel` laws; the
  theorem holds for glibc if glibc's (mangled) layout is one such model, which `locality` and
  `unique` express (only the `jmp_buf` bytes matter, and they determine the context).
* **The `cgocallback` contract** (`CgoCallback`): `runtime.cgocallback` (pinned by content)
  enters the exported Go function as an ABIInternal call `fn(frame)` on a goroutine stack that is
  not C memory (`CallbackEntry.stackSep`; `goStack` on amd64: `cbGoStack` writable bytes and the
  return slot), leaves the C memory outside `cbClobber` (the C stack below `SP` — at most
  `cbStackScratch = 16384` bytes —, its argument slots and the TLS `g` slot) as it was, and
  returns to `crosscall2` with only `SP` (and the thread, `MXCSR`/x87 control word on amd64)
  restored. The goroutine stack being outside the C state's memory is a modelling assumption: a
  precondition that granted the goroutine's stack to the C code would not describe a real
  execution. The Go side may itself only call stubs of its contract `Cin` (`Contract.none` in
  the examples), and Go code with frames needs at most `cbGoStack` bytes (larger frames are not
  covered).
* **Function-pointer hypotheses** (`CFuncIs`) are hypotheses in the statement (discharged by a
  proof of the concrete function, as `EArgMin.cmp_fn`), not trusted.

**The C calling conventions** (`Janus.CABI`, `Janus.Amd64.CABI`, the `CEnsures`/`CEnsuresR`
vocabulary) are specification definitions like `GoABI`. A `CEnsures`/`CEnsuresR` theorem is about
a call that follows the convention (`CCall`, `CCallA`). It promises what the convention requires
of the callee (`CReturn`: the callee-saved general registers, the low halves of `V8`–`V15` and
`FPCR` on arm64, the `MXCSR` control bits and the x87 control word on amd64) and nothing about
callers that violate the convention.

* *The classification is part of the specification.* Where a classified call puts an argument
  (`CCallA`, `ArgsAt … sig.passing`) and where a result comes back (`Returned`) is computed by
  the Lean functions `Janus.C.AAPCS64.assignAll`/`result` and `Janus.C.SysV.assignAll`/`result`.
  A theorem is only as meaningful as the agreement of these functions with the compilers that
  produce real call sites. That agreement is *tested*, not proved: `scripts/cabi-probe.sh`
  checks argument and result locations, layouts, `AL` and the `va_list` evolution against gcc
  15.2 and clang 21 at `-O0`/`-O2` on both ISAs (FFI.md § 1.3). Where a theorem's caller is
  itself extracted and verified (the cgo wrappers, `k_vsum8`), the classification is checked at
  that call site by the proof, so for those compositions the classification functions are not
  trusted: an error in them would make the proof fail.
* *Unspecified bytes.* Register bytes above an argument piece and stack bytes above a value in
  its slot are arbitrary in `CCallA` (the ABIs leave them unspecified; clang extends `char`/
  `short` arguments, gcc does not, and a callee may rely on neither), and a callee proof may not
  use them.
* *x87.* The amd64 state has the x87 control word (`State.fpucw`, reset `0x037F`; K1) and,
  since WP-J, the x87 register stack, tags and status word (`State.x87`). `FLDCW`/`FNSTCW` write
  and read `fpucw`; `CReturn` requires a C callee to preserve it. `CgoEntry.x87` (trusted) says
  the C code is entered with the Go caller's x87 stack (nothing between the Go call and the C entry
  executes an x87 instruction), so a C precondition such as `X87.Idle` (empty stack, nothing
  pending) is discharged by the same hypothesis on the Go call state; `GoResume` leaves the
  x87 stack and status arbitrary after the call (C may raise its sticky flags; Go code never
  reads them). A `long double` result in `ST(0)` is stated directly on `State.x87` (`CLdMul`);
  the classification's `PieceAt … (.x87 _)` is still `False`, so such a function has no
  `CEnsuresR` theorem yet.
* *Outside the classification.* Bit-fields, `__attribute__((packed))`/`aligned`, flexible
  arrays, empty structs and 32/64-byte vectors have no `CType`; a prototype using them cannot be
  stated.

## The kernel trust boundary (system calls, environment reads, traps)

Go programs reach Linux through `SVC #0` / `SYSCALL`, read time and identification registers
(`MRS CNTVCT_EL0`, `CNTFRQ_EL0`, `MIDR_EL1`, `DIT`; `CPUID`, `XGETBV`, `RDTSC(P)`), and call the
clock functions of the vDSO (code the kernel maps into the process, not part of the binary).
None of these has a result the user-mode state determines. The design (WP-C,
`Janus/Contracts/Syscall.lean`, `Janus/Contracts/SyscallAmd64.lean`):

* **The plain model stops.** `Arm64.step`/`Amd64.step` fault on every such instruction
  (`Fault.kernel`), so `Returns`, `Ensures` and every other plain predicate can never get past
  one. Traps (`BRK`, `UDF`, `INT3`, `UD2`, `HLT`) fault with `Fault.trap pc signal`: an explicit
  outcome, never an unconstrained state.
* **Stubs mark them.** The extractor puts a `.syscall` stub on every system-call and
  environment instruction inside the copied code, at its own address, and on the entry of the
  vDSO clock functions (`runtime.walltime`, `runtime.nanotime1`, amd64 `time.now`), which it
  authenticates like every runtime stub (name, ELF symbol table, uniqueness, normalized-code pin
  in `cmd/janus/stubpins_gen.go`). It puts a `.trap` stub on every trap instruction except the
  alignment padding after a function's last instruction. The placement is not trusted:
  `Kernel.siteOf` reads the instruction word at the stub and gives it a meaning only if it is
  the instruction the semantics expects (only the vDSO stubs are identified by name), and
  `Traps` checks that the word is a trap (`trapAt_faults`: executing it faults). A stub that is
  missing leaves the plain fault in place, which no theorem gets past.
* **The kernel is the environment.** `ReturnsK`/`EnsuresK` thread a kernel state `Kern`: an
  explicit I/O trace (`Event`s in order: writes, reads, opens, closes, clock readings, mappings,
  sleeps, environment reads), an input oracle per descriptor, a lower bound of
  `CLOCK_MONOTONIC`, the IDs, the signal mask, the alternate signal stack, `PSTATE.DIT`, the CPU
  features Linux reports and the page size. A theorem quantifies over **every** initial kernel
  state its precondition admits and holds for **every** successor the contracts allow at each
  stub. The contracts are relations written to over-approximate Linux:
  * **every call may fail** with any `-errno` (`IsErr`: `errno` 1 … 4094; Linux's largest
    user-visible `errno` is 133), changing nothing, except the calls Linux
    defines as infallible (`getpid`, `gettid`, `sched_yield`, `clock_gettime` of the two clocks
    Go reads into writable memory, the `close` of a descriptor, which always closes it);
  * `write` may write any prefix of the buffer (short writes), and the trace records exactly the
    bytes that were in memory at the call; `read` returns some prefix (possibly empty) of the
    descriptor's remaining input; `openat` returns any descriptor number below `2^31`, whose
    contents the environment chooses at that moment;
  * `mmap` returns any page-aligned address whose rounded-up range is disjoint from every region
    the model knows, below `2^47`; `munmap` and `madvise` act on whole pages (`Kern.pageSize`),
    and `madvise` may change every byte of the advised pages;
  * `CLOCK_MONOTONIC` and `CNTVCT_EL0` never go back; the wall clock, `MIDR_EL1`, `CPUID`,
    `RDTSC` are arbitrary (a thread may migrate between cores);
  * the vDSO wrappers may write the runtime-owned memory `KEnv.rt` (the `m`'s `vdsoPC`/`vdsoSP`,
    the `g0` and `gsignal` stacks) and `KEnv.stack` bytes below `SP`, and return with every
    register except `SP`, `g` and `FP` arbitrary (arm64 `EnsuresK` therefore uses `ABIReturnC`,
    without `X18`, as for C code).

  Each contract is satisfiable where its precondition holds (`Effect.total`, `SiteNext.total`
  on both ISAs) and allows the behaviour the specifications are about (`write_full`,
  `read_some`, `clock_monotonic`, `mmap_anon`); the runtime contracts around system calls are met
  by concrete code (`JanusTests/Kernel.lean`).
* **What is trusted.** That Linux behaves within these relations; that the vDSO clock functions
  return a clock reading and touch only the declared memory (their code is not in the binary);
  that `runtime.entersyscall`/`exitsyscall` (`SchedContract`) preserve the Go ABI registers and
  change only runtime-owned memory and their stack window, and that the goroutine's stack does not
  move while it is in a system call (the GC does not shrink the stack of a goroutine in a
  system call, and stack growth happens only at the stack checks); single-threaded execution (no
  other thread writes the program's memory or the descriptors meanwhile). The input oracle is a
  fixed stream per descriptor from its opening on: a file that grows while it is read (an EOF
  followed by more data) is outside the model only in that `read` may return 0 at any time, which
  the contract allows. Signals are not modelled (asynchronous preemption is trusted to restore
  the interrupted state; a delivered signal handler is runtime code).
* **What is not covered.** Unsupported system call numbers are not `SiteSafe`: no theorem gets
  past them. `exit_group` ends the run (`ReturnsK.halt`, with an explicit `onExit` predicate,
  `False` by default in `EnsuresK`). Signal delivery, `clone`, `futex` (concurrency, out of
  scope), file-system state and `ioctl`s are not modelled.
* **Environment instructions on the oracle.** The differential oracles run them natively: the
  model reports `kernel`, and the comparators check the hardware's result against the contract's
  frame (`compareEnv`/`compareEnv64`: only the destination registers change, with values in the
  contract's range; everything else, including memory and the flags, is unchanged; 0 mismatches,
  docs/ORACLE.md and docs/ORACLE-AMD64.md). `SVC`/`SYSCALL` are not run natively. `PUSHFQ` pushes
  `0x202` plus the status flags and `DF`; `POPFQ` faults (`Fault.systemFlag`) if it would set
  `TF`, `NT`, `AC` or `ID`, which the model does not track.

## Go assembly (ABI0)

A theorem about a Go assembly function is stated with `GoABI0.Ensures0` (or
`Amd64.GoABI0.Ensures0`), see [ABI0.md](ABI0.md). Every instruction of the assembly, of the Go
code calling it and of the ABI wrappers in between is executed by the model from the binary's
bytes; **no assembly-specific behaviour is assumed**. What the ABI0 vocabulary contributes is the
reading of the statement:

* *The call state.* `CallSetup0` says where an ABI0 caller puts the arguments (frame word `i` at
  `RSP + 8 + 8i`) and the return address, as `abi-internal.md`/`asm.html` and the code Go 1.26.0
  emits define it. A theorem is about calls of that shape; if a caller laid out the frame
  differently, the theorem would say nothing about that call. (When the caller is extracted too,
  as in `CallXor`, nothing about the layout is taken on trust: the caller's stores are executed.)
* *The return obligations.* `ABIReturn0` lists what the theorem promises to keep (arm64 `RSP`,
  `g`, `FP`, `R18`; amd64 `RSP + 8`, `RBP`, the `FS` base, `DF`). They are proved, not assumed.
  ABI0 promises nothing about `R14`/`X15` on amd64: a theorem about Go code after an ABI0 call
  obtains `R14 = g` from the precondition `GoABI.TlsG` (the TLS slot holds `g`), stated in the
  printed statement, and `X15 = 0` from the executed `XORPS`.
* *The callee summaries.* `Summary0` and `Ret0` are ordinary `Summary` statements about the
  extracted program, proved by execution; composing them (`janus_run calls [h]`) is the generic
  `Reaches.call` lemma. `Ensures0.of_summary` is a theorem.
* *The CLI classification* (`entryABI`/`entrySource`, the `Entry:` annotation, the convention
  warning) is untrusted and informational, like reachability. The warning reads the printed
  statement: it recognises `Ensures…` on `Extracted.program`, on `(Extracted.program.link impl)`
  and with exits (round 10 A1; before, only the first form warned), but an entry passed through a
  proof-local definition is not recognised. A theorem in the other convention verifies, and is
  about calls laid out that way, which no real caller makes.

Hence a theorem about assembly trusts exactly what a theorem about Go code trusts (the ISA model,
the extraction identity, Lean), plus the reading of `CallSetup0` above. The runtime's own
assembly that switches stacks or goroutines (`systemstack`, `mcall`, `gogo`, `asmcgocall`) is not
covered by the convention: a theorem about it needs a precondition describing those states.

## What the theorem does not say

* Nothing about callers other than those satisfying `CallSetup` and the stated precondition.
  If the precondition is unsatisfiable, the theorem is vacuous. Prefer preconditions that are
  shown satisfiable (`GoABI.setup_callSetup` builds a call state from any state).
* Nothing about timing, side channels, power, caches or speculative execution.
* Nothing about `NeverPanics` unless it is stated. `Returns` implies it
  (`GoABI.Returns.neverPanics`) only for the same initial state. `Panics` is only about panic
  stubs: a nil dereference is a `Fault`, and "never panics" means `NeverPanics` (no stub and no
  fault).
* Nothing about the Go source. If the compiler miscompiled it, the theorem is about the
  miscompiled code, which is the point.
